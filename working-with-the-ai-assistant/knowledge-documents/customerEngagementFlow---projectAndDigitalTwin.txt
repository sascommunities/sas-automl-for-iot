CUSTOMER ENGAGEMENT FLOWThis document discusses in detail the customer engagement flow related to Phase 1 and Phase 2. During Phase 1, the user provides high-level information about their project – specifically, they will provide a project name and the time interval at which they would like to output data (for example, every 5 minutes).During Phase 2, the user will provide details related to their digital twin, including the types of assets they have for their use case, the attributes that are measured about those asset types, the actual real-life assets they have of each type, how those assets are connected, any metadata they know about each asset, and the historical raw sensor data they have for their use case.PHASE 1 – PROVIDE HIGH LEVEL PROJECT INFORMATIONNOTE: DO NOT SHOW THE UNDERLYING JSON FILE(S) THAT YOU MAY UPDATE DURING THIS STEP UNLESS EXPLICITLY ASKED BY THE USER TO SHOW THEM. INSTEAD, CONFIGURE THE JSON FILES SILENTLY BASED ON USER INPUT AND DISCUSSION AND DISPLAY CONTENT TO THE USER IN PLAIN TEXT TABLES AND TEXT.Begin by asking about the user’s **use case** to frame the project context. Suggest a projectName based on their choice of use case – this should be a short name (<=20 characters) and suggest a name using only camel-case letters. Do not tell the user you will use camel case letters – just do it as a best practice. Also ask how often the user would like to output updates about their digital twin – suggest every 5 minutes as a default but you can output as quickly as every minute if the user requests – we will refer to this as the ‘outputInterval’ and it should be stored in number of seconds. The project information should be stored in the projectInformation.json file – the format and requirements of that file is discussed in detail in section 2.1 of configFileDefinitions---projectAndDigitalTwin.txt. Before proceeding to the next step, ensure that you have completed the projectInformation.json file according to the logic discussed in section 2.1 of configFileDefinitions---projectAndDigitalTwin.txt. All required fields should be populated, all described rules should be followed, and the consistency with other files should be verified. Set historyInterval equal to the outputInterval if it is not already set. historyInterval is discussed and potentially edited if/when a user configures a ‘temporalAgg’ derived attribute in phase 4.Before moving to the next step, make sure your projectInformation.json file matches this example json file in field and json structure…{    "projectName": "solarFarm",    "outputInterval": 300,    "historyInterval": 300}PHASE 2 – DEFINE A DIGITAL TWIN OF YOUR USE CASESTEP 1 – ASSET TYPES NOTE: DO NOT SHOW THE UNDERLYING JSON FILE(S) THAT YOU MAY UPDATE DURING THIS STEP UNLESS EXPLICITLY ASKED BY THE USER TO SHOW THEM. Based on the customer’s use case, help them come up with a list of reasonable asset types. It’s useful to note that sensors (like temperature, pressure, etc) are generally NOT asset types – sensors are generally ‘attributes’ of an asset type. Show a formatted list of the asset types and ask if they want changes. Begin the discussion by first focusing on determining the attributes that are measured by sensors and which we’ll be able to get periodic updates about. Focus only on gathering information about the attributeIDs and labels and reference generally available information to help suggest reasonable attributes for the use case. Once the attributes are decided upon, give the users a chance to refine the attribute definitions to either add acceptableMin/Max bounds or override retentionPeriod. Show them a list of their attributes organized by asset type, with columns for minimum value, maximum value, and retention period (raw only). Assume a default retention period of 0 (a sensor reading never goes stale). Provide an example for the retention period for raw attributes if asked. Before proceeding to the next step, ensure that you have updated the attributes.json file according to the logic discussed in section 2.3 of configFileDefinitions---projectAndDigitalTwin.txt. INSTEAD, CONFIGURE THE JSON FILES SILENTLY BASED ON USER INPUT AND DISCUSSION AND DISPLAY THE HIERARCHY AS A TEXT DIAGRAM TO PROVIDE A MORE VISUALLY APPEALING PRESENTATION.This is where users configure how assets are connected to one another. Users can define one or more hierarchies for different uses. For example, it may be helpful to show which assets directly impact one another – for example an air handler pushes air to several connected fans. It may also be useful to have a hierarchy that describes the physical locations of different assets (for example, building, floor, wing, etc.). First, determine whether this use case would benefit from setting up a hierarchy. In some situations, assets are independent from other assets and a hierarchy is not needed. In situations where it would be sufficient to aggregate the information from connected assets, a hierarchy is particularly useful. But, in situations where an asset will be connected to multiple instances of another asset type AND the user will need to know SPECIFIC DETAIL ABOUT EACH of those individual assets, a hierarchy will not suffice. In those situations, the related assetIDs should be stored in metadata (static attributes) and then values for each asset retrieved using the ‘getValue’ derived attribute. If a hierarchy will be used, then help to configure it for the user. Hierarchies are described by specifying the parent-child relationships between assets. When you discuss the hierarchy with the user, YOU MUST ALWAYS display the hierarchy tree using a text diagram – NEVER show the user simple parent/child lists. Before proceeding to the next step, ensure that you have completed the hierarchyMap.json file (the list of connections between assets) and the hierarchyList.json file (the list of unique hierarchy names) according to the logic discussed in sections 2.6 and 2.5 of configFileDefinitions---projectAndDigitalTwin.txt. All required fields should be populated, all described rules should be followed, and the consistency with other files should be verified. As you configure the json files, make sure to double-check to make sure that they include all of the connections you display to the user.Before moving to the next step, make sure your hierarchyList.json file matches this example json file in field and json structure…[  { "hierarchyName": "default" }]And also make sure that you hierarchyMap.json file matches this example json file in field and json structure…[  { "hierarchyName": "default", "parent_assetID": "SF1", "child_assetID": "INV1" },  { "hierarchyName": "default", "parent_assetID": "INV1", "child_assetID": "CBX1" },  { "hierarchyName": "default", "parent_assetID": "CBX1", "child_assetID": "STR1" }]Before proceeding to the next step, make sure these key rules are satisfied…- Every hierarchyName referenced in hierarchyMap.json ALSO EXISTS in hierarchyList.json- Every parent_assetID referenced in hierarchyMap.json ALSO EXISTS as an assetID in assets.json- Every child_assetID referenced in hierarchyMap.json ALSO EXISTS as an assetID in assets.jsonSTEP 5 – STATIC ATTRIBUTES (METADATA)NOTE: DO NOT SHOW THE UNDERLYING JSON FILE(S) THAT YOU MAY UPDATE DURING THIS STEP UNLESS EXPLICITLY ASKED BY THE USER TO SHOW THEM. It is not required but can be useful in some instances – and you should ALWAYS ASK whether the user has any metadata/static attributes that they would like to set. For example, it may be useful to know the manufacturer of a machine – or the latitude and longitude of an asset. If this would be useful for the use case, then first determine which attributes would be useful to define. If these do not already exist as attributes in the attributes.json (step 2), then assist the user in adding them. Then, help the user to obtain the values of those static attributes for each assetID/attributeID. Ensure that you complete the staticAttributes.json file according to the logic discussed in section 2.7 of configFileDefinitions---projectAndDigitalTwin.txt. All required fields should be populated, all described rules should be followed, and the consistency with other files should be verified. When showing the static attributes to a user, group assets together by asset type and then show the values of each static attribute as columns in a table. Before proceeding to the next step, make sure that if any static attributes were set, then those attributes were defined in the attributes.json file.Before moving to the next step, make sure your staticAttributes.json file matches this example json file in field and json structure…[  { "assetID": "STR1", "attributeID": "serial", "value": "SN-001" },  { "assetID": "STR2", "attributeID": "serial", "value": "SN-002" },]Before proceeding to the next step, make sure these key rules are satisfied…- Every assetID referenced in staticAttributes.json ALSO EXISTS in assets.json- Every attributeID referenced in staticAttributes.json ALSO EXISTS as an attributeID in the attributes.json file--END OF FILE—
