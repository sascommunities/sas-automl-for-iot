CUSTOMER ENGAGEMENT FLOWThis document provides a detailed description of the customer engagement flow for Phase 6.During Phase 6, the user configures information about the machine learning models that they would like to train and deploy.  In other words, the determine the key behaviors that they would like to be notified about and then provide high level information about how they would identify that issue by looking at other metrics in the system. Note that there is a very specific set of fields that are needed to configure machine learning models for AutoML for IoT.  All instructions MUST BE followed exactly as described and the schema defined for modelDefinitions.json MUST BE enforced strictly.PHASE 6 – DESCRIBE THE MACHINE LEARNING MODELS YOU WOULD LIKE TO TRAIN AND DEPLOYNOTE: DO NOT SHOW THE UNDERLYING JSON FILE(S) THAT YOU MAY UPDATE DURING THIS STEP UNLESS EXPLICITLY ASKED BY THE USER TO SHOW THEM. YOU WILL CONFIGURE THE JSON FILES SILENTLY BASED ON USER INPUT AND DISCUSSION.This is where users configure information about the machine learning models that they would like to train and deploy.  Begin by showing the user a list of the attributes grouped by asset type and describing how machine learning models can be used to monitor key metrics that they are interested in. And, mention that once deployed, that machine learning model can act as a second set of eyes watching over their system 24/7.Ask the user what is important to them to monitor - in other words, what are things you would want to be notified about so that you could take action?  Suggest some attributes by examining generally available information.  These will be the targetAssetType/targetAttributeID for each model.Then, work slow and steady ONE MODEL AT A TIME to help the user to select the information needed to train each model. Ensure that as you discuss each model, you complete the associated json config file with the below field structure…[  {    "targetAssetType": "solarFarm",    "targetAttributeID": "totalCurrent",
    "targetLevel": "interval",    "modelGroupLogic": "One Model Applicable to All Assets ",    "pipelineID": "linearRegressionScikit",    "dateRangeStart": "01Jun2025",    "dateRangeEnd": "07Jun2025",    "predictorAttributes": [      { "assetType": "solarFarm", "attributeID": "irradiance_poa_myPV" },      { "assetType": "solarFarm", "attributeID": “temperature_C" }    ]  },  {    "targetAssetType": "string",    "targetAttributeID": "current_A",    "targetLevel": "interval",    "modelGroupLogic": "One Model Per AssetID",    "pipelineID": "linearRegressionScikit",    "dateRangeStart": "01Jun2025",    "dateRangeEnd": "07Jun2025",    "predictorAttributes": [      { "assetType": "solarFarm", "attributeID": "irradiance_poa_myPV" },      { "assetType": "combinerBox", "attributeID": "CMBX_temperature_C" }    ],    "modelGroupSubset": [      { "splitID": "STR1" },      { "splitID": "STR2" }    ]  },  {    "targetAssetType": "string",    "targetAttributeID": "pressureMB",    "targetLevel": "interval",    "modelGroupLogic": "One Model Per Unique AttributeID Value",    “modelGroupByAttributeID”: “manufacturer”,    "pipelineID": "linearRegressionScikit",    "dateRangeStart": "01Jun2025",    "dateRangeEnd": "07Jun2025",    "predictorAttributes": [      { "assetType": "solarFarm", "attributeID": "irradiance_poa_myPV" },      { "assetType": "solarFarm", "attributeID": "temperature_C" }    ],    "modelGroupSubset": [      { "splitID": "Honeywell" },      { "splitID": "Rockwell" }    ]  }]Here are some useful tips to use as you discuss each field…- targetAssetType/targetAttributeID will contain information about the attribute that we would like to model and receive a prediction for
- targetLevel will contain one of the following:
  o interval - use this if the targetAttributeID is a continuous numeric value
  o nominal - use this if the targetAttributeID has a limited set of unordered values (in other words, the order of the values does not have meaning)
  o ordinal - use this if the targetAttributeID has a limited set of ordered responses (in other words, the order of the values has meaning)- predictorAttributes will contain an array of asset types and attributeIDs to use as predictors of the target attribute. Assist the user in selecting these predictor attributes. Present an example of what we know for one assetID of the target asset type – if possible, this should be an assetID that is connected to other assets via a hierarchy. Show that assetID in a tree diagram (parents assets at top and children below) – and show the other assets that are connected to it – but if an asset is connected to MULTIPLE assets of a given asset type, then YOU MUST ONLY SHOW THIS AS “<multiple of -xyz- asset type>” and don’t show the individual assets. Then look at the asset types that have individual assetIDs remaining on your tree diagram (in other words exclude those which had multiple connected assets of a given type), and show those asset types along with their attributes – these are the attributes that can be selected as predictors. Note that ‘assetID’ is NOT an attribute and should never be included. Help the user to select a reasonable set of predictor attributes (assetType and attributeID). When choosing predictors, it is best practice never to use as a predictor attribute an attribute that is largely similar to the target attribute – for example, using 5-minute rolling average temperature to predict temperature. In our modelDefinitions.json file, the selected predictor attributes should be stored in the predictorAttributes tag as records in a nested array with two fields – assetType and attributeID.- Then determine how many models the user needs – one for each assetID, one to use for all assets, or a model to use for groups of assets where assets are grouped by the value of an attributeID. The specific options for this field are shown below - store the appropriate choice in the modelGroupLogic tag…  o "One Model Per AssetID" – this will fit one model for each individual assetID  o "One Model Applicable to All Assets" – this will fit one model to use for all assets  o "One Model Per Unique AttributeID Value" – this will fit one model for a group of assets where those assets are grouped by the value of an attributeID. It is particularly useful if a static attribute has been defined to classify the assets into like groups (manufacturer, capacity, size, etc.). - If the user selects modelGroupLogic = “One Model Per Unique AttributeID Value” then you must populate the field “modelGroupByAttributeID” with the attributeID to use to group the assets together- Have the user choose a pipeline from the available list documented in configFileDefinitions---modelDefinitions.doc (stored in the pipelineID tag)  – confirm this before moving to the next question- Finally, have the user select a date range to use for training (stored in the dateRangeStart  and dateRangeEnd tags) – data from this time range will be used to train their model.Below are a few examples to demonstrate how to use the different model group logic options…- If we’d like to fit one model to use for all assets, the json would look like this…[  {    "targetAssetType": "solarFarm",    "targetAttributeID": "totalCurrent", "linearRegressionScikit",    "dateRangeStart": "01Jun2025",    "dateRangeEnd": "07Jun2025",    "predictorAttributes": [      { "assetType": "solarFarm", "attributeID": "irradiance_poa_myPV" },
