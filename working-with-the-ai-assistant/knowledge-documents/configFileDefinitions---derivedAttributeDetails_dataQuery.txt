1. IntroductionThis document defines how to configure and validate the detailed configurations derived attributes that allow you to query information from connected assets. These include…* getValue – navigates to a value from another asset via defined logic* searchEvents – allows the user to search all sensor readings that occurred during a specified time period rather than only the values that were current at the times of the output or history interval time periods). Users can return specific readings (newest, 2nd newest, etc., oldest, 2nd oldest, etc., min, max), calculate the average or sum of those readings over a time period, or obtain the timestamp that a specific value was observed.2. Configuration File Schemas, Rules, and ExamplesEach subsection includes Purpose and Considerations, Required Fields, Optional Fields, Validation Rules, Special Notes, and an Example. FOR THE FILES DESCRIBED IN EACH SECTION…* YOU MUST STRICTLY INCLUDE FIELDS THAT ARE REQUIRED* YOU MUST ENSURE THAT NO ADDITIONAL FIELDS ARE INCLUDED BESIDES THOSE THAT ARE DOCUMENTED AS REQUIRED OR OPTIONAL* YOU MUST STRICTLY FOLLOW THE DATA TYPES (STRING OR NUMERIC) FOR EACH FIELD* YOU MUST STRICTLY FOLLOW THE DESCRIPTION OF EACH FIELD* YOU MUST STRICTLY FOLLOW THE VALIDATION RULES AS DESCRIBED * YOU MUST STRICTLY FOLLOW THE EXAMPLE STRUCTURE OF THE JSON FILES-----
Derived Attribute Type:  getValuePurpose and ConsiderationsDefines the details needed to compute a ‘getValue’ derived attribute. Attributes of type ‘getValue’ are created to copy the value from another assetID/attributeID. Users can define logic to either search the hierarchies for the assetType/attributeID of interest OR they can specify an attributeID (typically a static attribute) for the same assetID which holds another assetID to retrieve the value from. This can be useful in several instances. For example, in some applications, an asset may be connected to another temporarily. For example, a patient may be temporarily connected via a hierarchy to a hospital bed that measures blood pressure – this allows the blood pressure measurement to be copied over and become a patient measure. It can also be useful when a user wants to search one direction or another from each asset – for example when trying to find the pressure upstream and downstream of an air filter. And for flood prediction, typically it is necessary to look upstream to determine whether the water is rising there. A river segment may have metadata that stores the IDs of several upstream river segments – then the gauge height could be retrieved for each upstream river segment and stored in a consistent set of fields (for example, gaugeHt_upstreamSegment1) even though each asset has different upstream river segments.InstructionsFor derived attributes of type ‘getValue’, you will need to create a record in derivedAttributeDetails_getValue.json that describes the logic needed to compute the ‘getValue’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "combinerBox",        "attributeID": "lastIrradiance",        "targetAssetType": "solarFarm",        "targetAttributeID": "irradiance_poa_myPV",        "targetAttributeMetric": "currentValue",        "navMethod": "navigate",        "attribIDContainingKnownAssetID": null,        "hierarchyValue": "default",        "hierarchyAttributeID": "",                "chkThisAssetYN": "N",        "maxUpTrav": "5",        "exactUpYN": "N",        "maxDownTrav": "0",        "exactDownYN": "N"    }]Here are a few rules to keep in mind when configuring the ‘getValue’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for each assetID of that asset type.- A ‘getValue’ attribute navigates either to a specific assetID stored in another attribute or navigates a hierarchy using specific logic to obtain the value of a specified attribute. It is used to copy an attribute from another asset, particularly in situations where the connection between assets may change (a patient is connected/disconnected from a hospital bed) or where requesting that attribute without further logic would result in ambiguous results (for example requesting the river height from an upstream river segment where there are splits in the river).- Users choose the attribute they would like to obtain by specifying the targetAssetType, targetAttributeID- Users choose the metric they would like to obtain by specifying targetAttributeMetric with these options  o ‘currentValue’ – obtains the current value of the attribute (with retention period logic applied to have measures go stale after a certain period)  o ‘lastValue’ – obtains the last value of the attribute, regardless of retention period  o ‘lastTime’ – obtains the time (epoch microseconds) of the last measurement - Users can choose to either go directly to an assetID stored in a static attribute (‘knownAssetID’) or choose to navigate using a specific set of logic they provide (‘navigate’)- If the user chooses to pull the value from a knownAssetID, then they must specify the attributeID that will hold the assetID to examine in the field ‘attribIDContainingKnownAssetID’- If the user chooses to navigate using a specific set of logic, then they need to provide details on how to navigate, including all of these fields…o Users can choose to either…  * Navigate via a hardcoded hierarchy by specifying the hierarchyName in the ‘hierarchyValue’ field or  * Navigate via a hierarchy where the name of the hierarchy is stored in the ‘hierarchyAttributeID’ attribute for that asset.o The calculation is made for each assetID of the specified asset type – when the calculation is made for an assetID, navigation begins at that assetID. These options specify what to examine from there  * chkThisAssetYN – ‘Y’ means to check the asset itself, ‘N’ means do not check the asset  * maxUpTrav – up to how many steps can you navigate ‘up’ the hierarchy – in other words to parent assets  * exactUpYN – should only assets that are exactly ‘maxUpTrav’ steps away be examined – ‘Y’ examines only assets that many levels away, while ‘N’ examines all assets found during that navigation  * maxDownTrav – up to how many steps can you navigate ‘down’ the hierarchy – in other words to child assets  * exactDownYN – should only assets that are exactly ‘maxDownTrav’ steps away be examined – ‘Y’ examines only assets that many levels away, while ‘N’ examines all assets found during that navigationRequired fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* targetAssetType (string) – the asset type for the attributeID that the user would like to obtain the value for. Must be a valid asset type in assetTypes.json.* targetAttributeID (string) – the raw or derived attribute to obtain the value for. The targetAssetType/targetAttributeID must match an assetType/attributeID in the attributes or derivedAttributes json files* targetAttributeMetric (string) – ‘currentValue’ retrieves the current value of the attributeID (retention period enforced if raw), ‘lastValue’ retrieves the last value of the attributeID (regardless of when received), ‘lastTime’ retrieves the time in epoch microseconds for when the last value was received, ‘assetID’ retrieves the assetID, ‘assetLabel’ retrieves the assetLabel* navMethod – ‘navigate’ will navigate the hierarchy from the asset, ‘knownAssetID’ will obtain the value from the assetID specified in the assetID’s field named <attribIDContainingKnownAssetID>* if navMethod=’knownAssetID’, then the user should complete this field…  o attribIDContainingKnownAssetID  (string) – this should contain a valid attributeID - assetType/attribIDContainingKnownAssetID should be a valid assetType/attributeID in the attributes file or derivedAttributes file* if navMethod=’navigate’, then the user should complete these fields to describe the logic to be used to navigate the hierarchy…  o chkThisAssetYN (string) – ‘Y’ means to include this assetID in the search, ‘N’ means to not include this assetID in the search  o maxUpTrav (string – numbers will be presented as text) – what is the maximum number of levels to navigate up the hierarchy – valid values are >=0  o exactUpYN (string) – ‘Y’ means navigate exactly the ‘maxUpTrav’ levels to find the value of interest, ‘N’ means find the first value found while navigating up with a matching assetType/attributeID  o maxDownTrav (string – numbers will be presented as text) – what is the maximum number of levels to navigate down the hierarchy – valid values are >=0  o exactDownTrav (string) – ‘Y’ means navigate exactly the ‘maxDownTrav’ levels to find the value of interest, ‘N’ means find the first value found while navigating down with a matching assetType/attributeID  AND EITHER THIS FIELD…  o hierarchyValue (string) – if populated, then search connections in the hierarchyMap json using this value as the hierarchyName. The value must be a valid hierarchyName in hierarchyList.json    OR THIS FIELD…  o hierarchyAttributeID (string) – if populated, then search connections in the hierarchyMap json using hierarchyName = [the value of that assetID’s ‘hierarchyAttributeID’]. The assetType/hierarchyAttributeID must match an assetType/attributeID in either attributes or derivedAttributesOptional fields* noneValidation rules* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘getValue’* The targetAssetType/targetAttributeID must exist as an assetType/attributeID in the attributes.json or derivedAttributes.json files* if hierarchyAttributeID is specified, then assetType/hierarchyAttributeID must be a valid assetType/attributeID in either attributes.json or derivedAttributes.json* if attribIDContainingKnownAssetID is specified, then assetType/attribIDContainingKnownAssetID must match as assetType/attributeID in either attributes.json or derivedAttributes.json* if navMethod=’knownAssetID’, then the user should complete attribIDContainingKnownAssetID* if navMethod=’navigate’, then the user should complete chkThisAssetYN, maxUpTrav, exactUpYN, maxDownTrav, exactDownTrav AND EITHER hierarchyValue or hierarchyAttributeIDExample[    {        "assetType": "combinerBox",        "attributeID": "lastIrradiance",        "targetAssetType": "solarFarm",        "targetAttributeID": "irradiance_poa_myPV",        "targetAttributeMetric": "currentValue",        "navMethod": "navigate",        "attribIDContainingKnownAssetID": null,        "hierarchyValue": "default",        "hierarchyAttributeID": "",                "chkThisAssetYN": "N",        "maxUpTrav": "5",        "exactUpYN": "N",        "maxDownTrav": "0",        "exactDownYN": "N"    }]-----
Derived Attribute Type:  searchEventsPurpose and ConsiderationsDefines the details needed to compute a ‘searchEvents’ derived attribute. Attributes of type ‘searchEvents’ are created to allow the user to search all sensor readings that occurred during a specified time period for an attribute. Users can choose to return a particular reading (oldest, 2nd oldest, etc., newest, 2nd newest, etc., min, max), to summarize the average or sum using ALL READINGS that were observed, or to obtain the time that a specific value was observed. This can be useful in several instances – to find the minimum or maximum by looking at all readings, to calculate the average value based on all observed readings, to retrieve the most recent reading, second most recent reading, etc., oldest reading in past hour, second oldest reading in past hour, etc, or to obtain the time that a specific value was observed. This is unique because all other derived attributes examine only sensor readings that were current as of the historyInterval or outputInterval time periods – this attribute examines all readings.InstructionsFor derived attributes of type ‘searchEvents’, you will need to create a record in derivedAttributeDetails_searchEvents.json that describes the logic needed to compute the ‘searchEvents’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "string",        "attributeID": "timeOfLastZeroCurrent",        "targetAttributeID": "current_A",        "queryAssetIDFromThisAttribID": "",        "oldTimePeriod": "3600",        "recentTimePeriod": "0",        "maxEventsToSearch": "100",        "searchLogic": "newest",        "returnValue": "value",        "instanceNumber": "1",        "searchSubsetValue": "0",        "searchSubsetAttributeID": ""    }]Here are a few rules to keep in mind when configuring the ‘searchEvents’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for each assetID of that asset type.- A ‘searchEvents’ attribute searches all updates that occurred for an attribute rather than only the ones that were current as of the output or history time intervals. Users can use this derived attribute to identify the oldest, 2nd oldest, etc., newest, 2nd newest, etc., min, or max or to calculate the average or sum based on all updates received, or to obtain the time that a specific value was observed.- Users choose the attribute they would like to obtain by specifying the targetAttributeID.- If the user prefers to search information for a different related assetID, then they can specify the attributeID that will hold the related assetID in the field ‘attribIDContainingKnownAssetID’ – the calculation will then instead examine the assetID held in the field ‘attribIDContainingKnownAssetID’. - Users choose a time range to examine by specifying oldTimePeriod and recentTimePeriod. These are stored in number of seconds ago, so oldTimePeriod should be greater than recentTimePeriod.- The individual updates about the attributeID will be stored in memory to allow for their search – maxEventsToSearch specifies a maximum number of records to maintain for that search. This should be set just large enough to safely capture the number of records that would normally be expected within the desired time interval.- Generally users will choose one of these options…  o Search for the minimum value by choosing searchLogic=’min’ and returnValue=’value’  o Search for the maximum value by choosing searchLogic=’max’ and returnValue=’value’  o Search for the oldest value by choosing searchLogic=’oldest’ and returnValue=’value’. If this option is selected, then users must also specify an instanceNumber – ‘1’ would mean to obtain the oldest, ‘2’ would mean to obtain the 2nd oldest etc.  o Search for the newest value by choosing searchLogic=’newest’ and returnValue=’value’. If this option is selected, then users must also specify an instanceNumber – ‘1’ would mean to obtain the newest, ‘2’ would mean to obtain the 2nd newest etc.  o Search for the time of the minimum value by choosing searchLogic=’min’ and returnValue=’time’  o Search for the time of the maximum value by choosing searchLogic=’max’ and returnValue=’time’  o Search for the time of the oldest value by choosing searchLogic=’oldest’ and returnValue=’time’. If this option is selected, then users must also specify an instanceNumber – ‘1’ would mean to obtain the oldest, ‘2’ would mean to obtain the 2nd oldest etc.  o Search for the time of the newest value by choosing searchLogic=’newest’ and returnValue=’time’. If this option is selected, then users must also specify an instanceNumber – ‘1’ would mean to obtain the newest, ‘2’ would mean to obtain the 2nd newest etc.  o Calculate the average value by choosing searchLogic=’avg’ and returnValue=’value’. Each update in this calculation is given equal weight when calculating the average – even if they occur very close together – therefore the average computed by the temporalAgg derived attribute is generally more accurate.  o Calculate the sum by choosing searchLogic=’sum’ and returnValue=’value’. Each update in this calculation is given equal weight when calculating the average – even if they occur very close together – therefore the average computed by the temporalAgg derived attribute is generally more accurate.  o Obtain the time a specific value was observed by specifying the value to search for using searchSubsetValue or searchSubsetAttributeID, by choosing searchLogic=’oldest’ or ‘newest’, choosing an instanceNumber, and choosing returnValue=’time’Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* targetAttributeID (string) – this must be a raw attribute and is the attributeID to obtain the value for. The assetType/targetAttributeID must match an assetType/attributeID in the attributes files. Derived attributes may not be referenced here.* oldTimePeriod (string – integer stored as text) – this is the beginning of the time period to search – in number of seconds ago * recentTimePeriod (string – integer stored as text) – this is the end of the time period to search – in number of seconds ago * maxEventsToSearch (string – integer stored as text) – this is the max number of events to maintain in memory and search through* searchLogic (string) – contains one of these possible options – min, max, oldest, newest, avg, sum.   o min – obtains the minimum value observed during the specified time period  o max – obtains the maximum value observed during the specified time period  o oldest – obtains the oldest value observed during the specified time period. Users can choose an instanceNumber to specify whether to return the first oldest, 2nd oldest, etc.  o newest  – obtains the most recent value observed during the specified time period. Users can choose an instanceNumber to specify whether to return the first newest, 2nd newest, etc.  o avg – calculates the average value from the values observed during the specified time period by giving each update equal weight  o sum – calculates the sum of the values observed during the specified time period by giving each update equal weight* returnValue (string) – contains either ‘time’ or ‘value’ – if searchLogic is ‘avg’ or ‘sum’ or ‘min’ or ‘max’, then the only valid choice is ‘value’  o ‘time’ – means to return the time the selected value was observed in UTC microseconds  o ‘value’ – means to return the selected value (min, max, oldest, newest) or the calculated value (avg, sum)* instanceNumber (string – integer stored as text) – this is required if searchLogic is ‘oldest’ or ‘newest’ – it provides information as to which record to return – ‘1’ means to return the oldest or newest record (depending on choice) – ‘2’ means to return the second oldest or newest, etc.Optional fields* attribIDContainingKnownAssetID  (string) – this allows the calculation to search a different related assetID – if used, it should contain a valid attributeID - assetType/attribIDContainingKnownAssetID should be a valid assetType/attributeID in the attributes file or derivedAttributes file* searchSubsetValue (string) – if the user chooses returnValue = ‘oldest’ or ‘newest’, then the user can choose to subset to only search for a specific value – effectively searching for the oldest or newest instance of the subset value * searchSubsetAttributeID (string) – if the user chooses returnValue = ‘oldest’ or ‘newest’, then the user can choose to subset to only search for a specific value – effectively searching for the oldest or newest instance of the subset value. In this case, the search value is stored in another attributeID searchSubsetAttributeID.Validation rules* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘searchEvents’* The assetType/targetAttributeID must exist as an assetType/attributeID in the attributes.json (not in derivedAttributes)* if attribIDContainingKnownAssetID is specified, then assetType/attribIDContainingKnownAssetID must match as assetType/attributeID in either attributes.json or derivedAttributes.json* oldTimePeriod and recentTimePeriod should be integers greater than or equal to 0* oldTimePeriod should be greater than recentTimePeriod* maxEventsToSearch must be an integer greater than 0* if returnLogic is ‘oldest’ or ‘newest’, then the user must also specify an instanceNumber. If specified, instanceNumber must be an integer >0. ‘1’ means to obtain the oldest/newest, ‘2’ means to obtain the 2nd oldest/newest, etc.* returnValue must be ‘value’ if returnLogic in (min, max, avg, sum). returnValue can be ‘value’ or ‘time’ if returnLogic in (oldest, newest)Example – calculating the minimum temperature based on all readings[    {        "assetType": "combinerBox",
