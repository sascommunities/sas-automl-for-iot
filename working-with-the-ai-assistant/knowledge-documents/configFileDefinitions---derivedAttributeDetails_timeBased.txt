1. IntroductionThis document defines how to configure and validate the detailed configurations derived attributes that focus on retrieving or summarizing values across time. These include…* lag – retrieve the value of an attribute from a specified prior time period* delta – calculate the difference in an attribute between two prior time periods* temporalAgg – aggregate an attribute across a specified prior time period2. Configuration File Schemas, Rules, and ExamplesEach subsection includes Purpose and Considerations, Required Fields, Optional Fields, Validation Rules, Special Notes, and an Example. FOR THE FILES DESCRIBED IN EACH SECTION…* YOU MUST STRICTLY INCLUDE FIELDS THAT ARE REQUIRED* YOU MUST ENSURE THAT NO ADDITIONAL FIELDS ARE INCLUDED BESIDES THOSE THAT ARE DOCUMENTED AS REQUIRED OR OPTIONAL* YOU MUST STRICTLY FOLLOW THE DATA TYPES (STRING OR NUMERIC) FOR EACH FIELD* YOU MUST STRICTLY FOLLOW THE DESCRIPTION OF EACH FIELD* YOU MUST STRICTLY FOLLOW THE VALIDATION RULES AS DESCRIBED * YOU MUST STRICTLY FOLLOW THE EXAMPLE STRUCTURE OF THE JSON FILES-----
Derived Attribute Type:  lagPurpose and ConsiderationsDefines the details needed to compute a ‘lag’ derived attribute. Attributes of type ‘lag’ are created to store the value of another attributeID from some time period ago.InstructionsFor derived attributes of type ‘lag’, you will need to create a record in derivedAttributeDetails_lag.json that describes the logic needed to compute the ‘lag’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "combinerBox",        "attributeID": "lag1HrCombinerBoxTemp",        "maxHistorySeconds": null,        "targetAttributeID": "CMBX_temperature_C",        "timePeriodAssetType": null,        "timePeriodAttributeID": null,        "timePeriodNumeric": "3600"    },    {        "assetType": "combinerBox",        "attributeID": "lag1HrCombinerBoxTemp",        "maxHistorySeconds": “1800”,        "targetAttributeID": "CMBX_temperature_C",        "timePeriodAssetType": “controlPanel”,        "timePeriodAttributeID": “lineSpeed”,        "timePeriodNumeric": null    }]Here are a few rules to keep in mind when configuring the ‘lag’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for that assetID of that asset type.- A ‘lag’ attribute retrieves the value of the target attribute (targetAttributeID) from some time period ago- If a user wants to retrieve the value from a hardcoded number of seconds ago, enter that number of seconds in ‘timePeriodNumeric’ – it must be an integer (>0) multiple of outputInterval.- If a user wants to retrieve the value from previous time period where the number of seconds is stored in another attribute (this would be referred to as a ‘dynamic’ lag since that time period could change), then specify that attribute in timePeriodAssetType/timePeriodAttributeID). If the user chooses this, then you also need to set a maximum amount of time to allow it to look back – this is stored in ‘maxHistorySeconds’ and is used to limit the history needed.  This is especially useful in manufacturing applications where the line speed (and therefore the amount of time to look back for the lag) changes throughout the day.Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* targetAttributeID (string) – the attributeID whose prior value should be obtained. The assetType/targetAttributeID must exist as an assetType/attributeID in the attributes.json file or derivedAttributes.json file.The user must specify EITHER this field to retrieve the value from a hardcoded number of seconds ago…* timePeriodNumeric (number stored as a string) – the amount of time, in seconds ago, to obtain the value of the assetType/targetAttributeID. Must be an integer multiple of the outputInterval. If the user suggests a timePeriodNumeric that is not an integer multiple of the outputPeriod, then request that they do – and provide a suggestion closest to their original value (but greater than 0).OR SPECIFY ALL THREE OF THE FOLLOWING FIELDS to retrieve the value from a number of seconds ago that changes based on the value of another attribute… * timePeriodAssetType (string) – the combination of timePeriodAssetType and timePeriodAttributeID describes another assetType/attributeID – the value contained in that attributeID will be used as the amount of time, in seconds ago, to obtain the value of the assetType/targetAttributeID. timePeriodAssetType/ timePeriodAttributeID must match an assetType/attributeID in either attributes or derivedAttributes* timePeriodAttributeID (string) – the combination of timePeriodAssetType and timePeriodAttributeID describes another assetType/attributeID – the value contained in that attributeID will be used as the amount of time, in seconds ago, to obtain the value of the assetType/targetAttributeID. timePeriodAssetType/ timePeriodAttributeID must match an assetType/attributeID in either attributes or derivedAttributes* maxHistorySeconds (number stored as a string) – required if timePeriodAssetType and timePeriodAttributeID are specified – this provides a maximum number of seconds that the lag value will be obtained from (in order to limit how far back history needs to be maintained). Must be an integer multiple of the outputInterval.Optional fields* noneValidation rules* assetType must exist in the assetTypes json* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘lag’* assetType/targetAttributeID must exist either as a valid attribute in the attributes json or as a valid derived attribute in the derivedAttributes json* A user must specify valid options for either timePeriodNumeric or all three of timePeriodAssetType/timePeriodAttributeID/maxHistorySeconds* If specified, timePeriodAssetType/timePeriodAttributeID must match an assetType/attributeID in either attributes or derivedAttributes Example[    {        "assetType": "combinerBox",        "attributeID": "lag1HrCombinerBoxTemp",        "maxHistorySeconds": null,        "targetAttributeID": "CMBX_temperature_C",        "timePeriodAssetType": null,        "timePeriodAttributeID": null,        "timePeriodNumeric": "3600"    }]-----Derived Attribute Type:  deltaPurpose and ConsiderationsDefines the details needed to compute a ‘delta’ derived attribute. Attributes of type ‘delta’ are created to store the difference in another attribute between two different points in time.Instructions:For derived attributes of type ‘delta’, you will need to create a record in derivedAttributeDetails_delta.json  that describes the logic needed to compute the ‘delta’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "solarFarm",        "attributeID": "chgIrradianceLastHr",        "oldTimePeriodNumeric": "3600",        "recentTimePeriodNumeric": "0",        "targetAttributeID": "irradiance_poa_myPV"    }]Here are a few rules to keep in mind when configuring the ‘delta’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for that assetID of that asset type.- A ‘delta’ attribute stores the difference in the target attribute (targetAttributeID) from one time period to another.- You must provide the two time periods to compare in the fields oldTimePeriodNumeric and recentTimePeriodNumeric in terms of the number of seconds ago. oldTimePeriodNumeric will contain the older of these two time periods (in seconds) – it must be an integer multiple of the outputInterval (>0)  and it will be the larger of the two values. recentTimePeriodNumeric will contain the more recent time period (in seconds) – it must be an integer multiple of the outputInterval (>=0)  and it will be the smaller of the two values. - As an example, if a user wanted to calculate the change from 15 minutes ago (900 seconds) to right now, then oldTimePeriodNumeric would be “900” and recentTimePeriodNumeric would be “0”.Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* targetAttributeID (string) – the attributeID (from the same assetType) for which the difference in values should be computed. Must exist in the attributes.json file or derivedAttributes.json file.* oldTimePeriodNumeric (number stored as a string) – this is the older of the two points in time – in seconds ago. Must be an integer multiple of the outputInterval. If the user suggests an oldTimePeriodNumeric that is not an integer multiple of the outputInterval, then request that they do – and provide a suggestion closest to the value they suggested. This must be >0.* recentTimePeriodNumeric (number stored as a string) – this is the more recent of the two points in time – in seconds ago. Must be an integer multiple of the outputInterval. If the user suggests an recentTimePeriodNumeric that is not an integer multiple of the outputInterval, then request that they do – and provide a suggestion closest to the value they suggested. This just be >=0.Optional fields* (none)Validation rules* assetType must exist in the assetTypes json* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘delta’* assetType/targetAttributeID must exist either as a valid raw attribute in the attributes json or as a valid derived attribute in the derivedAttributes json* oldTimePeriodNumeric must be greater than recentTimePeriodNumericExample[    {        "assetType": "solarFarm",        "attributeID": "chgIrradianceLastHr",        "oldTimePeriodNumeric": "3600",        "recentTimePeriodNumeric": "0",        "targetAttributeID": "irradiance_poa_myPV"    }]-----
Derived Attribute Type:  temporalAggPurpose and ConsiderationsDefines the details needed to compute a ‘temporalAgg’ derived attribute. Attributes of type ‘temporalAgg’ are created to aggregate another attribute over a specified time window.Instructions:For derived attributes of type ‘temporalAgg’, you will need to create a record in derivedAttributeDetails_temporalAgg.json  that describes the logic needed to compute the ‘temporalAgg’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "string",        "attributeID": "avgCurrentLastHr",        "maxHistorySeconds": null,        "oldTimePeriodAssetType": null,        "oldTimePeriodAttributeID": null,        "oldTimePeriodNumeric": "3600",        "recentTimePeriodAssetType": null,        "recentTimePeriodAttributeID": null,        "recentTimePeriodNumeric": "0",        "summaryLogic": "avg",        "targetAttributeID": "current_A"    }]Here are a few rules to keep in mind when configuring the ‘temporalAgg’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for each assetID of that asset type.- A ‘temporalAgg’ attribute stores the aggregation (min, max, avg, sum) of values for the target attribute (targetAttributeID) across some specified time period – for example, the average temperate over the past hour.- The field ‘summaryLogic’ holds the calculation logic to use – it must be ‘min’, ‘max’, ‘avg’, or ‘sum’- The user must choose the two time periods to aggregate between – an older time period and a more recent time period.- For the older time period…  o If a user wants to specify a hardcoded number of seconds ago, then enter that number of seconds in ‘oldTimePeriodNumeric’ – it must be an integer (>0) multiple of outputInterval.  o If a user wants to obtain the number of seconds ago from another attribute, then specify that attribute in oldTimePeriodAssetType/oldTimePeriodAttributeID. This is a useful option if the older of the two time periods depends on when something else occurred – which could be held in that attribute (in number of seconds ago).- For the more recent time period…  o If a user wants to specify a hardcoded number of seconds ago, then enter that number of seconds in ‘recentTimePeriodNumeric’ – it must be an integer (>=0) multiple of outputInterval.  o If a user wants to obtain the number of seconds ago from another attribute, then specify that attribute in recentTimePeriodAssetType/recentTimePeriodAttributeID. This is a useful option if the more recent of the time periods depends on when something else occurred – which could be held in that attribute (in number of seconds ago).- If the user chooses to obtain either time period from another attribute (rather than provide a hardcoded value), then you also need to set a maximum amount of time to allow it to look back – this is stored in ‘maxHistorySeconds’ and must be an integer (>0) of the outputInterval.Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* targetAttributeID (string) – the attributeID (from the same assetType) for which to aggregate values over a specified time window. The assetType/targetAttributeID must match an assetType/attributeID in either the attributes.json file or derivedAttributes.json file.* summaryLogic (string) – "sum", "avg", "min", "max".THE USER MUST EITHER SPECIFY THIS FIELD to aggregate over a time period where the oldest value to be considered is a hardcoded number of seconds ago…* oldTimePeriodNumeric (number stored as a string) – this is the beginning of the time period to aggregate – in seconds ago. If specified, this must be >0.OR SPECIFY BOTH OF THESE FIELDS to aggregate over a time period where the oldest value to be considered changes based on the value of another attribute …* oldTimePeriodAssetType (string) – the combination of oldTimePeriodAssetType and oldTimePeriodAttributeID describes another assetType/attributeID – the value contained in that attributeID will be used as the beginning of the time period to aggregate – in seconds ago* oldTimePeriodAttributeID (string) – the combination of oldTimePeriodAssetType and oldTimePeriodAttributeID describes another assetType/attributeID – the value contained in that attributeID will be used as the beginning of the time period to aggregate – in seconds agoTHE USER MUST ALSO SPECIFY EITHER THIS FIELD to aggregate over a time period where the most recent value to be considered is a hardcoded number of seconds ago…* recentTimePeriodNumeric (number stored as a string) – this is the end of the time period to aggregate – in seconds ago. If specified this must be >= 0.OR SPECIFY BOTH OF THESE FIELDS to aggregate over a time period where the most recent value to be considered changes based on the value of another attribute …* recentTimePeriodAssetType (string) – the combination of recentTimePeriodAssetType and recentTimePeriodAttributeID describes another assetType/attributeID – the value contained in that attributeID will be used as the end of the time period to aggregate – in seconds ago* recentTimePeriodAttributeID (string) – the combination of recentTimePeriodAssetType and recentTimePeriodAttributeID describes another assetType/attributeID – the value contained in that attributeID will be used as the end of the time period to aggregate – in seconds agoAND… IF oldTimePeriodAssetType and oldTimePeriodAttributeID are specified and/or recentTimePeriodAssetType and recentTimePeriodAttributeID are specified THEN THE USER MUST SPECIFY THIS FIELD…* maxHistorySeconds (number stored as a string) – this provides a maximum number of seconds that history will be maintained for and must be greater than 0 if specifiedOptional fields* noneValidation rules* assetType must exist in the assetTypes json* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘temporalAgg’* assetType/targetAttributeID must exist either as a valid raw attribute in the attributes json or as a valid derived attribute in the derivedAttributes json* The user must specify EITHER oldTimePeriodNumeric or both oldTimePeriodAssetType and oldTimePeriodAttributeID* The user must specify EITHER recentTimePeriodNumeric or both recentTimePeriodAssetType and recentTimePeriodAttributeID* If both oldTimePeriodNumeric and recentTimePeriodNumeric are specified, then oldTimePeriodNumeric must be > recentTimePeriodNumeric* If oldTimePeriodAssetType and oldTimePeriodAttributeID are specified, then oldTimePeriodAssetType/oldTimePeriodAttributeID must exist either as a valid raw attribute in the attributes json or as a valid derived attribute in the derivedAttributes json* If recentTimePeriodAssetType and recentTimePeriodAttributeID are specified, then recentTimePeriodAssetType/recentTimePeriodAttributeID must exist either as a valid raw attribute in the attributes json or as a valid derived attribute in the derivedAttributes json* If oldTimePeriodAssetType or oldTimePeriodAttributeID or recentTimePeriodAssetType or recentTimePeriodAttributeID is specified, then maxHistorySeconds must also be specified.Special Notes* IF A USER SPECIFIES ANY ‘temporalAgg’ derived attribute, THEN YOU MUST DO THE FOLLOWING… CONFIRM HOW GRANULAR THEY WOULD LIKE TO CALCULATE TEMPORAL AGGREGATIONS BY UPDATING THE historyInterval DEFINED EARLIER. * The ‘historyInterval’ controls how granular history is maintained. In other words, if I want the rolling 15-minute average, should that be an average of three measurements spaced 5 minutes apart or 15 measurements spaced one minute apart. This time interval is referred to as the ‘historyInterval’. The ‘historyInterval’ MUST be set so that ‘outputInterval’ is an integer multiple (>=1) of it. The same ‘historyInterval’ must be used for ALL temporal aggregations. And ALL numeric time intervals MUST be integer multiples (>=1) of the ‘historyInterval’. Example[    {        "assetType": "string",        "attributeID": "avgCurrentLastHr",        "maxHistorySeconds": null,        "oldTimePeriodAssetType": null,        "oldTimePeriodAttributeID": null,        "oldTimePeriodNumeric": "3600",        "recentTimePeriodAssetType": null,        "recentTimePeriodAttributeID": null,        "recentTimePeriodNumeric": "0",        "summaryLogic": "avg",        "targetAttributeID": "current_A"    }]--END OF FILE--
