CUSTOMER ENGAGEMENT FLOWThis document discusses in detail the customer engagement flow related to Phase 3. During Phase 3, the user will configure a subset of historical data with each record containing one of the following:- Update an individual sensor measurement (typical)- Add or delete an asset (selected use cases only)- Add or delete a connection between two assets (selected use cases only)For most uses cases, once defined, the assets and connections do not change. However, for some use cases, it may be the case that the assets and/or connections themselves also may change regularly – for example, adding or deleting assets or adding or deleting connections between assets. This can easily be accommodated for in the historical data by using a few additional optional fields. PHASE 3 – CREATE AN EXAMPLE HISTORICAL RAW SENSOR DATASETThis is where users configure a subset of historical data. For most use cases, each record will contain an update about the measurement for a single sensor. In some use cases, however, the assets and/or connections themselves may change over time – if this is the case, then each record in the historical data may update one of the following…- Update an individual sensor measurement, or- Add or delete an asset, or- Add or delete a connection between two assetsHelp the user either import a set of data and adjust the data so it is in the format shown in section 2.8 of configFileDefinitions---historicalData.txt – or to generate a sample of data which follows the format shown in section 2.8 of configFileDefinitions---historicalData.txt. Note that records in the historical dataset are always sorted non-descending by timestamp. The historical csv file is used to replay historical data as if it were live – and that data can be used to train analytical models. The historical data csv is NEVER used when running in real-time. ALWAYS SHOW a sample of the historical data to the user – and ALWAYS make sure that example file is sorted in non-descending order by the timestamp. ALWAYS describe to the user key features about the file – what the fields contain and that the file is sorted in order by timestamp so that it can be replayed as if it were live real-time data. Before proceeding to the next step, ensure that you have completed the historicalData.csv file according to the logic discussed in section 2.8 of configFileDefinitions---historicalData.txt. All required fields should be populated, all described rules should be followed, and the consistency with other files should be verified. Before moving to the next step, make sure that the records in your historicalData.csv file match one or more of these examples in field and file structure…. If updating an individual sensor measurement, the records should look like this…I,N,1,data,1714492800000000,STR1,current_A,7.8I,N,1,data,1714492801000000,STR1,current_A,7.9I,N,1,data,1714492802000000,STR1,current_A,8.0If adding or deleting an assetID, the records should look like this…I,N,1,updateAssets,1672530700000000,,,,add,16003832,patient,16003832,Y,,,,,I,N,1,updateAssets,1672530700000000,,,,delete,16482223,patient,16482223,Y,,,,,I,N,1,updateAssets,1672530700000000,,,,add,19112135,patient,19112135,Y,,,,,If adding or deleting a connection between two assets, the records should look like this…    I,N,1,updateConnections,1672530800000000,,,,,,,,,add,hospitalPatient,hospital,<->,10933622    I,N,1,updateConnections,1672530800000000,,,,,,,,,delete,hospitalPatient,hospital,<->,11536727    I,N,1,updateConnections,1672530800000000,,,,,,,,,add,hospitalPatient,hospital,<->,11902171Before proceeding to the next step, also make sure these key rules are satisfied…- The historicalData.csv file MUST NOT have a header row. The first row should contain a data record.- Every assetID referenced in historicalData.csv ALSO EXISTS in assets.json- Every attributeID referenced in historicalData.csv ALSO EXISTS as an attributeID in the attributes.json file--END OF FILE—
