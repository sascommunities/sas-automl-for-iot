High-Level Description of AutoML for IoT:You will configure a digital twin of your use case, define logic to enrich the raw sensor data, define structured output datasets, and specify high-level information about the ML models you would like to train and deploy.At the end of the process, you will be provided with a consolidated json config file that you can import into AutoML for IoT which will then complete all necessary steps and create the real-time deployment for your analysis using a fully automated process. Using this json file, AutoML for IoT will create all of following artifacts for youÉ- Structured analytic-ready datasets focused on each of your asset types- Trained models using the model pipelines you choose (or even custom design) from either SAS Model Studio or Python. If trained using a Model Studio pipeline, then those models will be automatically managed by Model Manager.- A deployable real-time SAS Event Stream Processing Project which can be deployed using SAS Event Stream Manager. SAS Event Stream Manager also has an option to deploy the project in a fully self-contained docker container on a VM or on the edge.How AutoML for IoT Works:Below is high-level detail related to how AutoML for IoT worksÉ- AutoML for IoT maintains a digital twin of the use case Ð a picture of the connected assets with each of those assets having measurable attributes. - As the sensor measurements (attributes) change, the digital twin is updated to reflect the new data so that it always reflects the most current data.- At a regular interval (the outputInterval Ð for example, every minute), additional derived attributes are calculated based on information in the digital twin Ð for example, data can be summarized across time, across connected assets, and custom SAS code can even be executed. Together, the raw sensor information and the derived attributes provide a comprehensive picture of the use case.- At that same output interval (immediately after the derived attributes are calculated), data is output from the digital twin into structured output datasets that the user has defined. A dataset can be output focused on each asset type Ð but each dataset can retrieve information from that asset type and/or connected asset types. As a result, the user can quickly obtain structured output datasets that are easy to use for dashboarding or for model training.- If a user would like to train a machine learning model to predict an outcome, then those models are described by the user via a few simple inputs Ð target variable, predictor variables, time range to train on, etc. Those models are automatically trained Ð and the resulting predictions and standard errors are added to the output datasets.- Finally, a deployment-ready SAS Event Stream Processing project is automatically written, loaded into ESP, and can even be set running.- All of the steps above are completed based on just a few json configuration files which this AI assistant helps to create.Example Use Cases:Below are a few example use cases which have been delivered using AutoML for IoTÉ- Solar Farm AnalyticsUse a small solar farm project with 1 solar farm (irradiance), 2 inverters (no sensors), 4 combiner boxes (temperature), and 8 strings (electrical current) of solar panels. Calculate a rolling average of the string current, combiner box temperature, and solar farm irradiance, and aggregate (sum) the rolling average of the current up to the other levels of the hierarchy. Design output datasets for EACH asset type that contain all attributes from that asset type as well as connected *parent* asset types. Define models that predict each rolling average current measure or aggregate rolling average current measure as a function of the rolling average irradiance Ð and for strings and combiner boxes, also use the rolling average of the combiner box temperature as a predictor. - HVAC AnalyticsUse a small HVAC system with 2 air handlers (supply fan speed, supply fan kw, duct pressure, supply air temperature) Ð each connected to 4 fan powered boxes (zone temp, zone setpoint, airflow, damper position). Calculate a new air handler metric that is the sum of the airflow from connected fpbs. Calculate a new fpb metric that is the difference between zone temp and setpoint. Design output datasets for EACH asset type that contain all attributes from that asset type as well as connected *parent* asset types. Define a model for ahus that predicts supply fan kw as a function of supply fan speed and duct pressure.  Define another model for fpbs that predicts airflow as a function of the difference between zone temp and setpoint and the supply air temperature.- Flood PredictionUse a small example from the Neuse River in North Carolina Ð search the available river gauge sensors available via USGS to determine a few river segments. Set the river segments up with asset type = river segment and attribute = gauge height. No hierarchy will be needed for this use case since we will capture information about related assets as metadata instead. Set up static attributes for the river segments named upstream1 and upstream2 that hold the assetID of up to 2 upstream river segments. Also set up static attributes for each river segment containing the latitude and longitude of the river segments. Create a corresponding weather station (asset type = ÔweatherStationÕ) for the location of each river gauge. Assign the latitude and longitude for these to be the same as the corresponding river segment. For each weather station, capture the precipitation and forecasted precipitation as raw sensors. Set up static attributes for the river segments named wthStation0, wthStation1 and wthStation2 that hold the assetID of the weather station associated with this river segment (wthStation0) and the weather stations of the upstream1 and upstream2 river segments (wthStation1 and wthStation2 respectively). Create a derived attribute for river segment that calculates the change in gauge height over the past hour / 2 hours / 3 hours. Use getValue derived attributes to obtain the gauge height and change in gauge height for the upstream segments by examining the upstream1 and upstream2 values. Use getValue derived attributes to obtain the precipitation and forecast precipitation for the three weather stations by examining the wthStation0, wthStation1, and wthStation2 values. Predict the change in a river segmentÕs gauge height as a function of the changes occurring for this and the upstream segments as well as the rain that has occurred in the past few hours at each weather station.- ManufacturingUse a manufacturing process project focused on manufacturing sprockets with stages organized in a flow (melting -> molding -> cooling -> finishing -> testing -> batch). Capture sprocket material properties, temperatures, and production measurements across each stage. Compute derived features such as temperature averages, process durations, material removed, and quality metrics. Monitor both batches as they dynamically move through the plant and an always monitoried batch that reflects current values at the plant. Create outputs for each stage and a batch-level dataset, and build models to predict batch pass/fail outcomes using process and material features.- HealthcareUse a healthcare monitoring project with hospital units and patients organized in a hierarchy (unit -> patient). Capture patient vitals, lab results, and demographics such as age and gender. Compute temporal features including rolling averages, lags, and deltas for key measurements, along with clinical indicators like abnormal vital counts, hypotension flags, and worsening lab trends. Design patient-level output datasets that include all raw and derived attributes, and define a single machine learning model to predict sepsis risk using these features for early warning.
- TransportationUse a transit network project that models a subway system as connected track segments between platforms. Each platform and segment includes geospatial attributes (latitude/longitude) to represent the physical layout of the network. As the project runs, dynamically introduce train assets and continuously update their connections to the track segments based on their current location, effectively tracking train movement through the network in real time. This setup allows you to think about the system as a connected graph, where you can analyze movement, flow, and conditions across adjacent segments. From there, you can derive features like segment-to-segment relationships (travel time, wait time, etc.) or route-level metrics (remaining travel time). You can then design outputs tables to monitor network performance, detect anomalies, or understand transit patterns across the system.
