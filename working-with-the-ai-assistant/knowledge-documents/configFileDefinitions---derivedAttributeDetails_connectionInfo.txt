1. IntroductionThis document defines how to configure and validate the detailed configurations needed to configure derived attributes that focus on retrieving information about the IDs, labels or counts of connected assets. These include…* getAssetID – retrieve the assetID of a connected asset of a particular type* getAssetLabel – retrieve the assetLabel of a connected asset of a particular type* countConn – count the number of connections (potentially subset to a specific asset type)* getConn – retrieve the assetID of a connected asset (potentially of a specific asset type)2. Configuration File Schemas, Rules, and ExamplesEach subsection includes Purpose and Considerations, Required Fields, Optional Fields, Validation Rules, Special Notes, and an Example. FOR THE FILES DESCRIBED IN EACH SECTION…* YOU MUST STRICTLY INCLUDE FIELDS THAT ARE REQUIRED* YOU MUST ENSURE THAT NO ADDITIONAL FIELDS ARE INCLUDED BESIDES THOSE THAT ARE DOCUMENTED AS REQUIRED OR OPTIONAL* YOU MUST STRICTLY FOLLOW THE DATA TYPES (STRING OR NUMERIC) FOR EACH FIELD* YOU MUST STRICTLY FOLLOW THE DESCRIPTION OF EACH FIELD* YOU MUST STRICTLY FOLLOW THE VALIDATION RULES AS DESCRIBED * YOU MUST STRICTLY FOLLOW THE EXAMPLE STRUCTURE OF THE JSON FILES-----
Derived Attribute Type:  getAssetIDPurpose and ConsiderationsDefines the details needed to compute a ‘getAssetID’ derived attribute. Attributes of type ‘getAssetID’ are created to obtain the assetID from a connected asset – for example, what is the assetID of my connected air handler. This is particularly useful to be able to output the IDs of connected assets to support dashboard creation. InstructionsFor derived attributes of type ‘getAssetID’, you will need to create a record in derivedAttributeDetails_getAssetID.json that describes the logic needed to compute the ‘getAssetID’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "string",        "attributeID": "combinerBoxID",        "targetAssetType": "combinerBox"    }]Here are a few rules to keep in mind when configuring the ‘getAssetID’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for each assetID of that asset type.- A ‘getAssetID’ attribute stores the assetID of the connected asset of asset type ‘targetAssetType’. For example, for a fan powered box, what is the assetID of my connected air handler. - This attribute type should only be used when the choice of the connected assetID would not be ambiguous – for example, an air handler has many connected fan powered boxes – I should not use getAssetID for air handlers to find my connected fan powered box as there would be multiple possible choices to return.Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* targetAssetType (string) – the asset type for which you would like to obtain the connected asset’s assetID. For example, for a fan powered box, obtain the assetID of its connected air handler. Must be a valid asset type in assetTypes.json.Optional fields* (none)Validation rules* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘getAssetID’* The targetAssetType must exist in the assetTypes json* This attribute type should not be used when it would be ambiguous to choose a single connected asset of that type – for example, if multiple assets of the target asset type are connected, it would not be clear which should be selected.Example[    {        "assetType": "string",        "attributeID": "combinerBoxID",        "targetAssetType": "combinerBox"    }]-----Derived Attribute Type:  getAssetLabelPurpose and ConsiderationsDefines the details needed to compute a ‘getAssetLabel’ derived attribute. Derived Attribute Type:  countConnPurpose and ConsiderationsDefines the details needed to compute a ‘countConn’ derived attribute. Attributes of type ‘countConn’ are created to obtain the count of the number of connected assets (children or parents). In some applications, the assetID of interest may instead be held in an attribute – and the calculation can be made by looking at the connections for THAT assetID. For example, in a train application, the train may have an attribute (currentStation) that holds the current station that the train is at. The user may want to query and find out the number of connections for the train station rather than for the train itself.Instructions:For derived attributes of type ‘countConn’, you will need to create a record in derivedAttributeDetails_countConn.json that describes the logic needed to compute the ‘countConn’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "array",        "attributeID": "combinerBoxCount",        "hierarchyValue": "default",    	 "hierarchyAttributeID": "",        "parentsOrChildren": "children",    	 "subsetAssetType": "",    	 "queryAssetIDFromThisAttribID": ""    }]Here are a few rules to keep in mind when configuring the ‘countConn’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for each assetID of that asset type.- A ‘countConn’ attribute obtains the number of parent or child connections for that assetID in a specific hierarchy. For example, how many patients are connected to this hospital. - Users can choose to either…  o count the connections in a hardcoded hierarchy by specifying the hierarchyName in the ‘hierarchyValue’ field or  o count the connections in a hierarchy where the name of the hierarchy is stored in the ‘hierarchyAttributeID’ attribute for the same asset type- Users can choose to count either the number of parents by specifying ‘parentsOrChildren’=’parents’ or count the number of children by specifying ‘parentsOrChildren’=’children’- Users can optionally choose to count only connections to assets of a specific asset type if they specify a value for the optional field ‘subsetAssetType’- While the calculation will be performed for each assetID of this asset type, we may actually be interested in determining the connections for a DIFFERENT RELATED assetID. For example, if we have a project with trains, stations, and people - and for each train, we want to know how many people are waiting at the next station, then can store the station in an attributeID ‘nextStation’ and then reference that attributeID in the field “queryAssetIDFromThisAttribID”. This would result in us computing, for each train, the number of people connected to the station stored in the attributeID ‘nextStation’.Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* parentsOrChildren (string) – ‘parents’ requests the number of connected parent assets and ‘children’ requests the number of connected child assets Users must specify EITHER a hardcoded hierarchy name…* hierarchyValue (string) – if populated, then count connections by examining connections in hierarchyMap json with hierarchyName = the value of this fieldOR obtain the name of the hierarchy to search from the value of another attributeID for the same assetType…* hierarchyAttributeID (string) - If populated, then count connections by examining connections in hierarchyMap.json with hierarchyName = [the value of that assetID’s ‘hierarchyAttributeID’]. For example, in a train application, there may be many possible routes (hierarchies). The route that this train is following currently might be held in an attributeID called ‘route’. And specifying ‘route’ here as the ‘hierarchyAttributeID’ would allow the connection count to be dynamic based on the ‘route’ of each specific train. The assetType/hierarchyAttributeID must match a valid assetType/attributeID in either the attributes.json file or the derivedAttributes.json file.Optional fields* subsetAssetType (string) – if a user would like to count only connected assets of a specific asset type, enter a valid asset type in this field. That assetType must exist in the assetTypes.json file.* queryAssetIDFromThisAttribID (string) – if a user would like to query information for a related asset – where that assetID is stored another attributeID, then enter the attributeID they would like to query here. For example, in a train application, the train may have an attribute (currentStation) that holds the current station that the train is at. The user may want to query and find out the number of connections for that train station and could reference ‘currentStation’ here. The assetType/queryAssetIDFromThisAttribID must be a valid assetType/attributeID in either the attributes.json file or the derivedAttributes.json file.Validation rules* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘countConn’* If hierarchyAttributeID  is specified, then assetType/hierarchyAttributeID must match an assetType/attributeID in either attributes.json or derivedAttributes.json* Only one of hierarchyValue and hierarchyAttributeID should be non-missing.* If specified, subsetAssetType must contain a valid asset type from the assetTypes json* If queryAssetIDFromThisAttribID  is specified, then assetType/queryAssetIDFromThisAttribID must match an assetType/attributeID in either the attributes.json or derivedAttributes.json files.Example[    {        "assetType": "array",        "attributeID": "combinerBoxCount",        "hierarchyValue": "default",    	 "hierarchyAttributeID": "",        "parentsOrChildren": "children",    	 "subsetAssetType": "",    	 "queryAssetIDFromThisAttribID": ""    }]-----Derived Attribute Type:  getConnPurpose and ConsiderationsDefines the details needed to compute a ‘getConn’ derived attribute. Attributes of type ‘getConn’ are created to obtain the assetID of a connected asset (child or parent). In some applications, the assetID of interest may instead be held in an attribute – and the calculation can be made by looking at the connections for THAT assetID. For example, in a train application, the train may have an attribute (currentStation) that holds the current station that the train is at. The user may want to query and find out a connection for the train station rather than for the train itself.Instructions:For derived attributes of type ‘getConn’, you will need to create a record in derivedAttributeDetails_getConn.json that describes the logic needed to compute the ‘getConn’ attribute. A fully-populated json schema for this attribute is shown below…[    {        "assetType": "array",        "attributeID": "combinerBoxID1",        "hierarchyValue": "default",        "hierarchyAttributeID": "",        "parentsOrChildren": "children",        "subsetAssetType": "combinerBox",        "instanceNumber": "1",        "searchLogic": "oldest",        "queryAssetIDFromThisAttribID": ""    }]Here are a few rules to keep in mind when configuring the ‘getConn’ record…- The derived attribute you are creating is denoted by the assetType/attributeID and must have a corresponding record in derivedAttributes.json. This means that this calculation will be made for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for each assetID of that asset type.- A ‘getConn’ attribute obtains the assetID of a parent or child connection for that assetID in a specific hierarchy. For example, what is the assetID of the first connected fan, or what is the assetID of the first train enroute to the destination. - Users can choose to either…  o count the connections in a hardcoded hierarchy by specifying the hierarchyName in the ‘hierarchyValue’ field or  o count the connections in a hierarchy where the name of the hierarchy is stored in the ‘hierarchyAttributeID’ attribute for that asset.- Users can choose to either obtain an assetID that is a parent asset by specifying ‘parentsOrChildren’=’parents’ or obtain an assetID that is a child asset by specifying ‘parentsOrChildren’=’children’- Users can optionally choose to examine only assets of a specific asset type if they specify a value for the optional field ‘subsetAssetType’- The user needs to specify which connection to retrieve in situations where more than one connection is found – users must specify an ‘instanceNumber’ (1, 2, 3, etc.) and ‘searchLogic’ to specify whether they would like to retrieve the ‘newest’ or ‘oldest’ connection. These fields are required even if the defined hierarchy contains just a single connection.- While the calculation will be performed for each assetID of this asset type, we may actually be interested in determining the connections for a DIFFERENT RELATED assetID. For example, if we have a project with trains, stations, and people - and for each train, we want to know which train is at the previous station, then can store the previous station in an attributeID ‘prevStation’ and then reference that attributeID in the field “queryAssetIDFromThisAttribID”. This would result in us obtaining, for each train, the ID of the train connected to the previous station stored in the attributeID ‘prevStation’.Required fields (per item)* assetType (string) – the assetType of the new attribute. Must be a valid asset type in the assetTypes json.* attributeID (string) – the attributeID of the new attribute. This field should contain only letters, numbers, spaces, underscores, and dashes.* parentsOrChildren (string) – ‘parents’ requests that a parent assetID be obtained and ‘children’ requests that a child assetID be obtained * searchLogic (string) – ‘oldest’ or ‘newest’. Connections are added to the list of parents or children as they are processed. ‘oldest’ will retrieve the connection added first and ‘newest’ will retrieve the connection added last.* instanceNumber (number stored as a string) – if there are multiple assetIDs found, which instance should be returned – must be an integer >0. If searchLogic=’oldest’ and instanceNumber=1 then the oldest connection (assetID) will be returned. Similarly if searchLogic=’newest’ and instanceNumber=1 then the newest connection will be returned.Users must specify EITHER a hardcoded hierarchy name…* hierarchyValue (string) – if populated, then search connections by examining connections in hierarchyMap json with hierarchyName = the value of this field. This must match a hierarchyName in hierarchyList.jsonOR obtain the name of the hierarchy to search from the value of another attributeID for the same assetType…* hierarchyAttributeID (string) - If populated, then search connections by examining connections in hierarchyMap.json with hierarchyName = [the value of that assetID’s ‘hierarchyAttributeID’]. For example, in a train application, there may be many possible routes (hierarchies). The route that this train is following might be held in an attributeID called ‘route’. And specifying ‘route’ here as the ‘hierarchyAttributeID’ would allow the search for connections to be dynamic based on the ‘route’ of each specific train. The assetType/hierarchyAttributeID must match an assetType/attributeID in either attributes.json or derivedAttributes.json.Optional fields* subsetAssetType (string) – if a user would like to only return a connected asset of a specific asset type, enter the asset type in this field – the value must match an assetType from the assetTypes.json file* queryAssetIDFromThisAttribID (string) – if a user would like to query information for a related assetID where that assetID is stored another attributeID, then enter the attributeID here. For example, in a train application, the train may have an attribute (currentStation) that holds the current station that the train is at. The user may want to query and find out a specific connections for that train station and could reference ‘currentStation’ here. The assetType/ queryAssetIDFromThisAttribID must be valid assetType/attributeID in either attributes.json or derivedAttributes.json.Validation rules* assetType/attributeID must match a record in derivedAttributes.json with attributeType ‘getConn’* If hierarchyAttributeID  is specified, then assetType/hierarchyAttributeID must match an assetType/attributeID in either attributes.json or derivedAttributes.json.* Only one of hierarchyValue and hierarchyAttributeID should be non-missing.* If specified, subsetAssetType must contain a valid asset type from the assetTypes json* If queryAssetIDFromThisAttribID is specified, then assetType/queryAssetIDFromThisAttribID must match an assetType/attributeID from either attributes.json or derivedAttributes.json.Example[    {        "assetType": "array",        "attributeID": "combinerBoxID1",        "hierarchyValue": "default",        "hierarchyAttributeID": "",        "parentsOrChildren": "children",        "subsetAssetType": "combinerBox",        "instanceNumber": "1",        "searchLogic": "oldest",        "queryAssetIDFromThisAttribID": ""    }]--END OF FILE--
