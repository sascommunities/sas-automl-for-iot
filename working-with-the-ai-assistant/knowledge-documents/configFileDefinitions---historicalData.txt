1. IntroductionThis document defines how to configure and validate each of the files that are needed for AutoMLforIoT. It covers the configuration file schemas, rules, and examples needed to configure the historical raw dataset (historicalData.csv).2. Configuration File Schemas, Rules, and ExamplesEach subsection includes Purpose and Considerations, Required Fields, Optional Fields, Validation Rules, Special Notes, and an Example. FOR THE FILES DESCRIBED IN EACH SECTION…* YOU MUST STRICTLY INCLUDE FIELDS THAT ARE REQUIRED* YOU MUST ENSURE THAT NO ADDITIONAL FIELDS ARE INCLUDED BESIDES THOSE THAT ARE DOCUMENTED AS REQUIRED OR OPTIONAL* YOU MUST STRICTLY FOLLOW THE DATA TYPES (STRING OR NUMERIC) FOR EACH FIELD* YOU MUST STRICTLY FOLLOW THE DESCRIPTION OF EACH FIELD* YOU MUST STRICTLY FOLLOW THE VALIDATION RULES AS DESCRIBED * YOU MUST STRICTLY FOLLOW THE EXAMPLE STRUCTURE OF THE JSON FILES-----
2.8 historicalData.csvPurpose and ConsiderationsThis file will contain historical raw sensor data – in other words, periodic updates about the assets / attributes described in the assets/attributes files. It is sorted nondecreasing by timestamp so that the data can be replayed in time order of those updates.This file is csv format and has no header row. The records in this file can be used to update a sensor reading for a specific assetID/attributeID (category=’data’), add or delete an assetID (category=’updateAssets’), or add or delete a connection between assets (category=’updateConnections’). The fields opcode, flag, index, category, and timestamp are used for all records. If updating a sensor reading, then the fields assetID, attributeID, and value are also used; if adding or deleting an asset, then the fields Column rules* opcode (string) – used by the streaming engine - must be "I" or "i" to indicate the record is an ‘insert’ record* flag (string) – used by the streaming engine - must be "N" or "n"to indicate the record is a ‘new’ record* index (numeric) = an integer key (this can be constant and often will just have index=1 for all records since the actual value is set by the streaming engine while running)* category (string) - must be "data" or “updateAssets” or “updateConnections”  o “data” is used to indicate that the record will update the value of an assetID/attributeID in the digital twin  o “updateAssets” is used to indicate that the record will add or delete an assetID  o “updateConnections” is used to indicate that the record will add or delete a connection between 2 assets* timestamp (numeric) = numeric epoch time in microseconds; file sorted nondecreasingif category=’data’ then these fields should be populated (otherwise they should be blank)…* assetID (string) – contains the assetID to update - typically exists in assets json (but not required)* attributeID (string) – contains the attributeID to update - typically exists in attributes json (but not required)* value (string or numeric) – holds the value to set the assetID/attributeID to – the value should match the dataType if the attributeID exists in the attributes fileif category=’updateAssets’ then these fields should be populated (otherwise they should be blank)…* updateAssetAction – indicates the action to take to update the asset list - must be 'add' or 'delete' or 'update'* updateAssetID – indicates the assetID to add/delete/update - should be an assetID from the assets.csv file* updateAssetType – indicates the assetType of the assetID - should be an assetType from the assetTypes.csv file* updateAssetLabel - the label to use for the assetID* updateAssetOutputRequired – must be ‘Y’ or ‘N’  - set to 'Y' if you'd like to output data for that asset  - set to 'N' if you would NOT like to output data for that assetif category=’updateConnections’ then these fields should be populated (otherwise they should be blank)…* updateConnectionAction – indicates the action to take to update the connections - must be 'add’ or 'delete' or 'update'* updateHierarchyName – indicates the hierarchy to update a connection in - must be a hierarchyName from the hierarchyList.csv file* updateParentAssetID – indicates the parent assetID in the connection - must be an assetID from the assets.csv file* updateDirection - can be one of 3 values‘-->’ - parent can navigate to child but child cannot navigate to parent‘<--' - child can navigate to parent but parent cannot navigate to child      ‘<->’ - navigation in either direction is supported* updateChildAssetID – indicates the child assetID in the connection - must be an assetID from the assets.csv fileValidation Rules:* Must be sorted in non-decreasing timestamp order* Must NOT contain a header row* assetID, updateAssetID, updateParentAssetID – if populated, the value must exist in the assets file* attributeID – if populated, the value must exist in the attributes file* updateAssetType – if populated, the value must exist in the assetTypes file* updateHierarchyName – if populated, the value must exist in the hierarchyList file* if any records are present with category=’updateAssets’ or category=’updateConnections’, then all fields must be provided even if blank. If all records have category=’data’, then only the first 8 fields are required (opcode, flag, index, category, timestamp, assetID, attributeID, value)Special Notes:* Raw data will be included in this file for all/many assets and attributes. DO NOT show the user raw data examples for individual sensors – instead, when showing an example of this file, show one consolidated example that includes several assets and attributes for several time periods (separated by the outputInterval number of seconds).* If you show the user a sample of the historical data, ALWAYS make sure that the example records are sorted in non-descending order by the timestamp.* When you discuss this file with the user, mention that AutoML for IoT builds two projects – one designed to run live and one that is designed to replay historical data. Many times, it is necessary to replay historical data in order to train analytical models. This is the format of the historical data – and when needed, it will be replayed *as if that data had arrived live*.ExamplesIf updating an individual sensor measurement, the records should look like this…I,N,1,data,1714492800000000,STR1,current_A,7.8I,N,1,data,1714492801000000,STR1,current_A,7.9I,N,1,data,1714492802000000,STR1,current_A,8.0If adding or deleting an assetID, the records should look like this…I,N,1,updateAssets,1672530700000000,,,,add,16003832,patient,16003832,Y,,,,,I,N,1,updateAssets,1672530700000000,,,,delete,16482223,patient,16482223,Y,,,,,I,N,1,updateAssets,1672530700000000,,,,add,19112135,patient,19112135,Y,,,,,If adding or deleting a connection between two assets, the records should look like this…I,N,1,updateConnections,1672530800000000,,,,,,,,,add,hospitalPatient,hospital,<->,10933622I,N,1,updateConnections,1672530800000000,,,,,,,,,delete,hospitalPatient,hospital,<->,11536727I,N,1,updateConnections,1672530800000000,,,,,,,,,add,hospitalPatient,hospital,<->,11902171--END OF FILE--
