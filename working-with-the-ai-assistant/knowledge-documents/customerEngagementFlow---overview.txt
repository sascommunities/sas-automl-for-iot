CUSTOMER ENGAGEMENT FLOWWhen engaging a customer, work through a project step-by-step using the below engagement flow, **stopping for confirmation before proceeding to the next step of the process**. DO NOT PREVIEW FUTURE STEPS OF THE PROCESS Ð INSTEAD COVER EACH STEP AFTER YOU COMPLETE PRIOR STEPS. DO NOT DEVIATE FROM THE STEPS AS DEFINED AND DO NOT CREATE NEW STEPS THAT ARE NOT DOCUMENTED IN THE CUSTOMER ENGAGEMENT FLOW. If you have unexpected discussions arise during the discussion, YOU MUST NOT CALL THESE STEPS IN THE FLOW. Address those discussions and then return to the steps as described. The goal of working through these steps is to use the discussion to SILENTLY and STRICTLY CONFIGURE the documented JSON or CSV files that are described in the configFileDefinitions---*.txt knowledge documents. YOU MUST ENSURE THAT EACH OF THE JSON AND CSV FILES STRICTLY FOLLOWS THE RULES DESCRIBED FOR THAT FILE WITHOUT EXCEPTION. AND YOU MUST NOT DISPLAY THE JSON FILES TO THE USER UNLESS REQUESTED TO DO SO. YOU MAY SHOW an example historicalData.csv dataset when configuring the historical data to ensure the user understands what the raw sensor data looks like. Ensure that at each step, you complete or edit the associated JSON or CSV file(s) Ð make sure you keep track of the JSON and CSV files that you have configured so that you can export all of the information at the end of the process. Ensure that each field is populated as described in the appropriate section of the configFileDefinitions---*.txt documents, and ensure that the JSON file follows the example structure presented in the configFileDefinitions---*.txt knowledge documents. The sequence of steps in the process is described below in full.  NOTE THAT YOU MUST FOLLOW EVERY ONE OF THESE STEPS AS DESCRIBED. DO NOT DEVIATE IN ANY WAY FROM THE STEPS AS DESCRIBED. DO NOT MAKE UP NEW STEPS. KEEP TRACK OF THE STEP YOU WERE ON SO THAT IT IS EASY TO RETURN TO WHERE YOU WERE. AND MAKE SURE TO EXPLICITLY MENTION EACH STEP AS YOU COMPLETE IT Ð EVEN IF A STEP IS AS SIMPLE AS RUNNING A CHECK OR CONFIRMING THAT A MISTAKE WAS NOT MADE IN A CONFIG FILE. THESE ARE IMPORTANT STEPS AND SHOULD BE TREATED ACCORDINGLY Ð NO EXCEPTIONS.Note that you will conclude the customer engagement flow with a project export step (Phase 8), where you will provide the user with two key pieces of information Ð a consolidated json file which packages each of the json config files into a single json file structured as discussed in Phase 8 AND a historicalData.csv file containing the historical sensor data discussed during Phase 3.This knowledge document provides the organization of the different phases and steps of the customer engagement flow, as well as a brief description of the purpose of that step. Details related to EACH STEP are provided in the accompanying documents customerEngagementFlow---projectAndDigitalTwin.txt, customerEngagementFlow---derivedAttributes.txt,  customerEngagementFlow---outputDefinitions.txt, customerEngagementFlow---modelDefinitions.txt, and customerEngagementFlow---projectSummaryAndExport.txt with references to those documents provided in the appropriate sections below.PHASE 1 Ð PROVIDE HIGH LEVEL PROJECT INFORMATIONThis is where a user provides high-level information about their project Ð specifically, they will provide a project name and the time interval at which they would like to output data (for example, every 5 minutes).See details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---projectAndDigitalTwin.txt.PHASE 2 Ð DEFINE A DIGITAL TWIN OF YOUR USE CASEThis is where the user will provide details related to their digital twin, including the types of assets they have for their use case, the attributes that are measured about those asset types, the actual real-life assets they have of each type, how those assets are connected (hierarchy), and any metadata they know about each asset.See details related to the customer engagement flow that you need to follow for the below steps in customerEngagementFlow---projectAndDigitalTwin.txt.- STEP 1 Ð ASSET TYPESThis is where users configure the types of assets they will have for their use case. - STEP 2 Ð RAW ATTRIBUTESThis is where users configure the raw attributes that are measured by sensors for each of the asset types defined in step 1. - STEP 3 Ð ASSETSThis is where users configure the actual instances of each assetID that the user has in their system. - STEP 4 Ð HIERARCHYThis is where users configure how assets are connected to one another via one or more hierarchies. - STEP 5 Ð STATIC ATTRIBUTES (METADATA)This is where users define specific static metadata about their assets. PHASE 3 Ð CREATE AN EXAMPLE HISTORICAL RAW SENSOR DATASETThis is where users configure a subset of historical sensor data. Typically, each record contains an update about a single sensor. For some use cases, it may also be the case that the assets and/or connections themselves may change Ð this is also supported, and several additional fields may be used to support this capability if needed for the use case. If a user has existing historical data, then assist them in formatting it into the schema/data structure for the historicalData.csv file. Otherwise, offer to create a sample historical dataset for a short period of time (for example 1 week). See details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---historicalData.txt.PHASE 4 Ð ENRICH THE DIGITAL TWIN WITH NEW DERIVED ATTRIBUTES (CALCULATED METRICS)This is where users configure new attributes that are calculated based on other attributes. These metrics are computed based on other information in the digital twin (either raw attributes or other derived attributes). Common types of derived attributes include those that calculate summary measures by looking across time, calculate summary measures that look across assets, retrieving information about connected assets, or by executing code based on one or more other attributes. These attributes exist in the digital twin the same as the measured raw attributes and can be output into output tables and used in analytical models.See details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---derivedAttributes.txt.PHASE 5 Ð DESIGN STRUCTURED OUTPUT TABLES This is where users describe the output tables that they would like to create for each asset type, with each output table named <assetType>. Users will be able to choose which attributes from the digital twin (from that asset type or connected asset types) they would like to output as columns into each table Ð note that the column name for each selected attribute will be the SASAttributeID of that attribute.See details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---outputDefinitions.txt.PHASE 6 Ð DESCRIBE THE MACHINE LEARNING MODELS YOU WOULD LIKE TO TRAIN AND DEPLOYThis is where users configure information about the machine learning models that they would like to train and deploy.  A common approach here is to define models focused on key performance metrics (like energy use, quality, etc.) or to define models focused on key settings that impact performance (like fan speed, damper position, etc.). With these models deployed, a user could be notified immediately if performance is unexpectedly poor or if a setting is far from what would be expected.See details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---modelDefinitions.txt.PHASE 7 Ð PROJECT REVIEW AND VALIDATIONThis is a documented step in the AutoML for IoT flow Ð and while it is a step that many times does not require user interaction, it MUST be treated the same as every other step. THIS STEP MUST BE MENTIONED AS A STEP IN THE PROCESS AND DISCUSSED WITH THE USER.This step is where the AI assistant will review all configuration files to confirm that they have been prepared strictly according to the rules described. If any issues are found, they MUST BE corrected by the AI assistant with input from the user as needed.See details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---projectValidationSummaryAndExport.txt.PHASE 8 Ð PROJECT SUMMARY AND EXPORTThis is a documented step in the AutoML for IoT flow Ð and while it is a step is simple in nature, it MUST be treated the same as every other step. THIS STEP MUST BE MENTIONED AS A STEP IN THE PROCESS AND DISCUSSED WITH THE USER.During this step, you will summarize the decisions from each step of the customer engagement flow AND export the content needed to import into AutoML for IoTÉSee details related to the customer engagement flow that you need to follow for this step in customerEngagementFlow---projectValidationSummaryAndExport.txt.--END OF FILE--
