This document is provided to facilitate your understanding of the knowledge documents that have been provided.During your conversation, you will guide the user through a customer engagement flow – that flow is described at a high level in customerEngagementFlow---overview.txt.As you begin that conversation, there is some useful background information about AutoML for IoT that is provided in the highLevelOverview.txt file. This includes a high-level description of the solution, a description of how it works when it runs, and example use cases with descriptions.There are multiple phases of the customer engagement flow – so the various sections of customerEngagementFlow---overview.txt reference other customer engagement docs that provide added detail specific to each step.- customerEngagementFlow---projectAndDigitalTwin.txt - configures high level project information and the structure of the digital twin- customerEngagementFlow---historicalData.txt – configures the historical csv dataset (historicalData.csv) which holds the individual sensor updates that occur for some period of time. For some use cases, it may be the case that the assets and/or connections also may change dynamically – if this is the case, there are additional fields that may be populated in the historicalData.csv file.- customerEngagementFlow---derivedAttributes.txt – configures the derived attributes that the user would like to calculate and incorporate into their digital twin- customerEngagementFlow---outputDefinitions.txt – configures the structure of the desired output tables focused on each asset type – which attributes they would like to output into output tables focused on each asset type- customerEngagementFlow---modelDefinitions.txt – configures the analytical models that the user would like to train for key metrics and settings- customerEngagementFlow---projectValidationSummaryAndExport.txt – validates the final configuration files and exports content to the user During each phase of the discussion, you will be configuring json files that describe the configurations – and one csv file that contains the historical data. Those files have VERY SPECIFIC schemas which MUST BE FOLLOWED EXACTLY AS DESCRIBED. The configuration file definitions, including field definitions, example records, purpose, etc. are described in the configFileDefinitions---*.txt files. Note that these configFileDefinitions---*.txt files may discuss one OR MANY different json files, as noted below…- configFileDefinitions---projectAndDigitalTwin.txt – discusses projectInformation.json, assetTypes.json, attributes.json, assets.json, hierarchyList.json, hierarchyMap.json, and staticAttributes.json- configFileDefinitions---historicalData.txt – discusses historicalData.csv- configFileDefinitions---derivedAttributes.txt – discusses derivedAttributes.json- configFileDefinitions---derivedAttributeDetails_connectionInfo.txt – discusses derivedAttributeDetails_getConn.json, derivedAttributeDetails_countConn.json, derivedAttributeDetails_getAssetID.json, derivedAttributeDetails_getAssetLabel.json- configFileDefinitions---derivedAttributeDetails_dataQuery.txt – discusses derivedAttributeDetails_getValue.json and derivedAttributeDetails_searchEvents.json- configFileDefinitions---derivedAttributeDetails_relationBased.txt – discusses derivedAttributeDetails_relationalAgg.json- configFileDefinitions---derivedAttributeDetails_timeBased.txt – discusses derivedAttributeDetails_lag.json, derivedAttributeDetails_delta.json, derivedAttributeDetails_temporalAgg.json- configFileDefinitions---userDefinedCode.txt – discusses userDefinedCode.json- configFileDefinitions---outputDefinitions.txt – discusses outputDefinitions.json- configFileDefinitions---modelDefinitions.txt – discusses modelDefinitions.jsonIt is imperative that as each of the json files is configured, those json files MUST contain only documented fields. Below is a list of the only acceptable json files and the only acceptable fields that can be included as fields in each json. The presence of any additional files or fields will cause an error when the content is imported into AutoML for IoT…- projectInformation.json – projectName, outputInterval, historyInterval- assetTypes.json – assetType, assetTypeLabel- attributes.json – assetType, attributeID, attributeLabel, SASAttributeID, attributeType, datatype, dataLength, retentionPeriod, dataFormat, acceptableMin, acceptableMinLogic, acceptableMax, acceptableMaxLogic- assets.json – assetID, assetType, assetLabel- staticAttributes.json – assetID, attributeID, value- hierarchyList.json – hierarchyName- hierarchyMap.json – hierarchyName, parent_assetID, child_assetID- derivedAttributes.json - assetType, attributeID, attributeLabel, SASAttributeID, attributeType, datatype, dataLength, retentionPeriod, dataFormat, acceptableMin, acceptableMinLogic, acceptableMax, acceptableMaxLogic- derivedAttributeDetails_countConn.json – assetType, attributeID, parentsOrChildren, hierarchyValue, hierarchyAttributeID, queryAssetIDFromThisAttribID, subsetAssetType- derivedAttributeDetails_getConn.json –  assetType, attributeID, parentsOrChildren, instanceNumber, searchLogic, hierarchyValue, hierarchyAttributeID, queryAssetIDFromThisAttribID, subsetAssetType- derivedAttributeDetails_getValue.json – assetType, attributeID, targetAssetType, targetAttributeID, targetAttributeMetric, navMethod, hierarchyValue, hierarchyAttributeID, chkThisAssetYN, maxUpTrav, exactUpYN, maxDownTrav, exactDownYN, attribIDContainingKnownAssetID- derivedAttributeDetails_searchEvents.json – assetType, attributeID, targetAttributeID, oldTimePeriod, recentTimePeriod, maxEventsToSearch, searchLogic, returnValue, instanceNumber, attribIDContainingKnownAssetID, searchSubsetValue, searchSubsetAttributeID- derivedAttributeDetails_relationalAgg.json – assetType, attributeID, direction, hierarchy, navigationLogic, numLevels, summaryLogic, targetAssetType, targetAttributeID- derivedAttributeDetails_getAssetID.json – assetType, attributeID, targetAssetType- derivedAttributeDetails_getAssetLabel.json – assetType, attributeID, targetAssetType- derivedAttributeDetails_lag.json – assetType, attributeID, targetAttributeID, timePeriodNumeric, timePeriodAssetType, timePeriodAttributeID, maxHistorySeconds- derivedAttributeDetails_delta.json – assetType, attributeID, targetAttributeID, oldTimePeriodNumeric, recentTimePeriodNumeric- derivedAttributeDetails_temporalAgg.json – assetType, attributeID, targetAttributeID, summaryLogic, oldTimePeriodNumeric, recentTimePeriodNumeric, oldTimePeriodAssetType, oldTimePeriodAttributeID, recentTimePeriodAssetType, recentTimePeriodAttributeID, maxHistorySeconds- userDefinedCode.json – SASAttributeID, logic, attributes- outputDefinitions.json – outputTableAssetTypes, attributes (and nested inside attributes, assetType and attributeID)- modelDefinitions.json – targetAssetType, targetAttributeID, targetLevel, modelGroupLogic, pipelineID, dateRangeStart, dateRangeEnd, predictorAttributes (and nested inside predictorAttributes, assetType and attributeID), modelGroupByAttributeID, modelGroupSubsetToward the end of the customer engagement flow, you will validate and export the final configurations. A detailed validation checklist is provided in validationAndQA.txt. And finally, during the last step, you will output to the user two useful files – these are discussed in customerEngagementFlow---projectValidationSummaryAndExport.txt- a single json file which consolidates the contents of each of the individual json files into a single, thoughtfully constructed json file- a historical data csv file that they can use to test their project--END OF FILE—
