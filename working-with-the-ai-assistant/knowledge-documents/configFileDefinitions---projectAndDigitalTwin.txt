1. IntroductionThis document defines how to configure and validate each of the files that are needed for AutoMLforIoT. It covers the configuration file schemas, rules, and examples needed to configure the - high-level project (projectInformation.json), and- digital twin (assetTypes.json, attributes.json, assets.json, hierarchyList.json, hierarchyMap.json, staticAttributes.json).2. Configuration File Schemas, Rules, and ExamplesEach subsection includes Purpose and Considerations, Required Fields, Optional Fields, Validation Rules, Special Notes, and an Example. FOR THE FILES DESCRIBED IN EACH SECTION…* YOU MUST STRICTLY INCLUDE FIELDS THAT ARE REQUIRED* YOU MUST ENSURE THAT NO ADDITIONAL FIELDS ARE INCLUDED BESIDES THOSE THAT ARE DOCUMENTED AS REQUIRED OR OPTIONAL* YOU MUST STRICTLY FOLLOW THE DATA TYPES (STRING OR NUMERIC) FOR EACH FIELD* YOU MUST STRICTLY FOLLOW THE DESCRIPTION OF EACH FIELD* YOU MUST STRICTLY FOLLOW THE VALIDATION RULES AS DESCRIBED * YOU MUST STRICTLY FOLLOW THE EXAMPLE STRUCTURE OF THE JSON FILES-----
2.1 projectInformation.jsonPurpose and ConsiderationsDefines high-level information about the project name, the output interval and the history interval.Required Fields* projectName (string) – a short project name (<=20 characters) containing only camel-case letters and numbers* outputInterval (number) – the time interval in seconds that output records should be output into output files – generally the default is 300 (seconds), but a user can choose to output as quick as 60 (seconds).* historyInterval (number) – the time interval in seconds to use to store historical data. By default, set this equal to the outputInterval and DO NOT ASK THE USER ABOUT IT OR SHOW IT TO THE USER. It will be discussed and potentially modified later if a user defines a derived attribute of type ‘temporalAgg’.Optional Fields- NoneValidation rules* outputInterval must be an integer multiple (>=1) of the historyIntervalSpecial Notes- Do not tell the user that you will recommend a camel case name for their project. Just do that as a best practice.Example{    "projectName": "solarFarm",    "outputInterval": 300,    "historyInterval": 300}-----
2.2 assetTypes.jsonPurpose and ConsiderationsDefines asset types and display labels. Asset types are the classes of things that will be needed for a customer’s use case. For example, for an HVAC system, this might include chillers, boilers, air handlers, etc. For a solar farm, this might include inverters, combiner boxes, and solar panels, etc. For a patient monitoring use case, this might include patients, hospitals, beds, doctors, etc.Never suggest making sensors/meters their own asset types. These must always be represented as attributes of the defined asset types – attributes are discussed and configured in the attributes.json file.Required fields* assetType (string) – unique ID – can contain letters and numbers – generally camelCase* assetTypeLabel (string) – human-readable label – should contain only letters, numbers, spaces, dashes, and underscoresOptional fields- NoneValidation rules* assetType should be unique across the file.Special Notes- NoneExample[  { "assetType": "solarFarm", "assetTypeLabel": "Solar Farm" },  { "assetType": "inverter", "assetTypeLabel": "Inverter" },  { "assetType": "string", "assetTypeLabel": "String" },  { "assetType": "combinerBox", "assetTypeLabel": "Combiner Box" }]-----
2.3 attributes.jsonPurpose and ConsiderationsDeclares raw measurable attributes for each asset type. These are either the attributes that the user will receive periodic updates about when the project runs in real-time – or attributes that will contain the static metadata that a user would like to set about each asset (for example, manufacturer, latitude/longitude, etc.).Required fields* assetType (string) – must exist in assetTypes.json* attributeID (string) – unique within the assetType – should contain only letters, numbers, spaces, underscores, and dashes * SASAttributeID (string) – should be <= 30 characters in length, [A-Za-z_][A-Za-z0-9_]** attributeType (string) - "raw" for all records* dataType (string) – should contain "double" if the attribute will contain a numeric value or "string" if the attribute will contain a string value* dataLength (number) – should be 8 if datatype=double; should be a positive integer if datatype=string (such that the string value is long enough to capture typical data for that attribute)* retentionPeriod (number, seconds; 0 = indefinite). This contains the amount of time (in seconds) until a sensor measurement is considered stale and that value should be forgotten. 0 means that a reading for that attribute will never go stale.Optional fields* dataFormat (string) – defined the format to be used when displaying results for that field - if populated, it must be a valid SAS format* acceptableMin, acceptableMax – sets the min/max acceptable value for the attribute. If specified, the corresponding acceptableMinLogic/acceptableMaxLogic field must also be set* acceptableMinLogic, acceptableMaxLogic – should be set IF an acceptable value was set. ‘limit’ means that values below the min or above the max are instead set to the min or max. ‘missing’ means that values below the min or above the max are ignored.Validation rules* assetType exists.* attributeID unique per assetType.* SASAttributeID unique per assetType.Special Notes- Retention period MUST only be discussed when attribute definitions are fine-tuned toward the end of a project’s configuration. When that happens, provide a short example of retention period – for example if we receive a temperature reading at 1:30 pm, at what time would we consider that reading to be old (stale) and no longer want to make use of that value. That amount of time in seconds is what is referred to as the retention period.- Acceptable min and max values MUST only be discussed when attribute definitions are fine-tuned at the end of a project’s configuration. If a user chooses a min or max, assume they will want to set the corresponding logic field to ‘missing’, but explain both the ‘limit’ and ‘missing’ options.Example[  {    "assetType": "string",    "attributeID": "current_A",    "SASAttributeID": "current_A",    "attributeType": "raw",    "dataType": "double",    "dataLength": 8,    "retentionPeriod": 0  },  {    "assetType": "solarFarm",    "attributeID": "irradiance_poa_myPV",    "SASAttributeID": "irradiance_poa_myPV",    "attributeType": "raw",    "dataType": "double",    "dataLength": 8,    "retentionPeriod": 0  },  {    "assetType": "combinerBox",    "attributeID": "CMBX_temperature_C",    "SASAttributeID": "CMBX_temperature_C",    "attributeType": "raw",    "dataType": "double",    "dataLength": 8,    "retentionPeriod": 0  }]-----
2.4 assets.jsonPurpose and ConsiderationsLists the individual assets that a user has for each defined asset type. These are the actual assets that exist of each type. Since attributes are defined for each asset type, each asset would be expected to have the attributes associated with that asset’s asset type.Required fields* assetID (string) – should be unique – must contain only letters, numbers, spaces, underscores, and dashes* assetType (string) – the value must exist in assetTypes file* assetLabel (string) – should contain only letters, numbers, spaces, underscores, and dashesValidation rules* assetID must be unique.* assetType must exist in the assetTypes file.Example[  { "assetID": "SF1", "assetType": "solarFarm", "assetLabel": "Solar Farm 1" },  { "assetID": "INV1", "assetType": "inverter", "assetLabel": "Inverter 1" },  { "assetID": "STR1", "assetType": "string", "assetLabel": "String 1" },  { "assetID": "CBX1", "assetType": "combinerBox", "assetLabel": "Combiner Box 1" }]-----
2.5 hierarchyList.jsonPurpose and ConsiderationsProvides a list of the hierarchies that are defined in the hierarchyMap file. Required fields* hierarchyName (string) – contains the name of each unique hierarchy – should contain only letters, numbers, underscores, and dashes – generally camelCaseValidation Rules- hierarchyName must be unique- These may include names not used in hierarchyMap.json.Example[  { "hierarchyName": "default" }]-----
2.6 hierarchyMap.jsonPurpose and ConsiderationsDefines parent–child asset links within each hierarchy. This defines how the assets are connected to one another. There is an additional field (direction) which describes whether child can navigate to parent, parent to child, or both.Required fields* hierarchyName (string) – the name of the hierarchy - must exist in hierarchyList.json* parent_assetID (string) – the parent assetID for the connection – this must exist in assets.json* child_assetID (string) – the child assetID for the connection – this must exist in assets.jsonValidation rules* hierarchyName must exist in the hierarchyList json* parent_assetID must exist in the assets json* child_assetID must exist in the assets jsonSpecial Notes- When planning out a hierarchy for a specific use case, generally it is best practice to define parent assets to be logically broader than the child assets.Example[  { "hierarchyName": "default", "parent_assetID": "SF1", "child_assetID": "INV1" },  { "hierarchyName": "default", "parent_assetID": "INV1", "child_assetID": "CBX1" },  { "hierarchyName": "default", "parent_assetID": "CBX1", "child_assetID": "STR1" }]-----
2.7 staticAttributes.json (optional)Purpose and ConsiderationsThis file defines the static metadata values stored per asset. The values included in this file are set when a project initiates – and generally the attributeID’s that are set will have a retentionPeriod of 0, which means that the values will be held indefinitely. staticAttributes are particularly useful to set information that are important (for example, manufacturer, latitude/longitude, etc.) but which will not typically change over time.Required fields* assetID (string) – the asset ID - must exist in the assets file* attributeID (string) – the attributeID to set the value of - must be a valid attributeID for the asset’s assetType in the attributes file* value (string) – contains the value of the static attribute - stored as a string regardless of whether the field is text or numbers. Example[  { "assetID": "STR1", "attributeID": "serial", "value": "SN-001" }]--END OF FILE--
