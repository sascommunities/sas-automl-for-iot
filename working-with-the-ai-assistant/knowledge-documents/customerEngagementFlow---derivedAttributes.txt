CUSTOMER ENGAGEMENT FLOWThis document discusses in detail the customer engagement flow for phase 4. The is where users configure new attributes that are calculated based on other attributes. These metrics are computed based on other information in the digital twin (either raw attributes or other derived attributes). Common types of derived attributes include those that calculate summary measures by looking across time, across assets, or by executing code based on one or more other attributes. These derived attributes will exist in the digital twin the same as the measured raw attributes and can be output into output tables and used in analytical models. Note that there is a very specific set of fields that are needed to configure the derived attributes for AutoML for IoT.  All instructions MUST BE followed exactly as described and the schemas defined for derivedAttributes.json, derivedAttributeDetails_*.json, and userDefinedCode.json MUST BE enforced strictly.PHASE 4 – ENRICH THE DIGITAL TWIN WITH NEW DERIVED ATTRIBUTES (CALCULATED METRICS)NOTE: DO NOT SHOW THE UNDERLYING JSON FILE(S) THAT YOU MAY UPDATE DURING THIS STEP UNLESS EXPLICITLY ASKED BY THE USER TO SHOW THEM. YOU WILL CONFIGURE THE JSON FILES SILENTLY BASED ON USER INPUT AND DISCUSSION.This is where users configure new attributes that are calculated based on other attributes. Before engaging the user on defining the derived attributes they might want to define, first review the following high-level description of the different types of attributes that are available to the user. Never suggest creating a derived attribute which is not supported by the existing attribute types. The types of derived attributes can be grouped according to their high-level purpose, as discussed below…- Calculate a new attribute by retrieving or summarizing *values over time* (these are documented in configFileDefinitions---derivedAttributeDetails_timeBased.txt). Examples are…  o ‘lag’ which retrieves a value from some prior time period ago (for example, what was the temperature 5 minutes ago),  o ‘temporalAgg’ which summarizes (avg, min, max, sum) an attribute over some period of time (for example, what was the average temperature over the past hour), and   o ‘delta’ which calculates the change in an attribute from one specific time period to another (for example, how much did the river height increase over the past hour). Note that the amount of time for a ‘lag’ attribute or the start or end time of a ‘temporalAgg’ attribute may EITHER BE a constant number (like 15 minutes) or a DYNAMIC number that is retrieved from another attribute (for example, a value that changes regularly based on the speed of a manufacturing line).- Calculate a new attribute by searching or summarizing values *across connected assets* where those connections are defined via a hierarchy (these are documented in configFileDefinitions---derivedAttributeDetails_relationBased.txt). Examples are…  o ‘relationalAgg’ navigates a specified hierarchy to aggregate values for a specific assetType/attributeID – and then calculates a sum/min/max/avg based on the values found. For example, what is the sum of the airflow for all connected fans. - Obtain information about an asset’s connections (these are documented in configFileDefinitions---derivedAttributeDetails_connectionInfo.txt). Examples include…  o ‘getAssetID’ and ‘getAssetLabel’ – obtain the ID or label of a connected piece of equipment – for example, what is the name of my connected air handler. This should only be used if the request is not ambiguous – in other words, if there are many assets that are connected of that asset type and it would not be obvious which ID to return.   o ‘countConn’ - obtain information about the number of connections  o ‘getConn’ - obtain the specific assetID of a connection- Calculate a new attribute by searching or querying to obtain information about an attribute for a connected asset (these are documented in configFileDefinitions---derivedAttributeDetails_dataQuery.txt). Examples are…  o ‘getValue’ navigates to a specific assetType/attributeID or assetID using logic provided by the user and stores the result. For example, what is the air pressure prior to or after an air filter or what is the gauge height of a specific river segment upstream. With this attribute type, there are two main options…     * A user can assign as metadata (static attribute) the specific assetID(s) that they would like to query (for example ‘upstreamRiverSegmentID’), then they can create a ‘getValue’ attribute which specifically queries that assetID – for example what is the river height of the assetID stored in the attribute ‘upstreamRiverSegmentID’.     * A user can specify navigation logic re: how to search the hierarchy for the requested value – for example search only parents up to 3 levels away or search child assets up to 2 levels away. This is useful if you have the same measurement potentially BOTH as parent and as child – for example, to find the differential pressure across an air filter, I would want to create one ‘getValue’ derived attribute that obtains the pressure by searching assets one level up and create a second ‘getValue’ derived attribute that obtains the pressure by searching assets one level down – and then calculate the difference between the two using a ‘code’ derived attribute.    * As you can see, this attribute type can be especially valuable in situations where the user would like to obtain the value of an attribute for a connected asset and navigating a hierarchy may lead to ambiguous results (in other words, multiple parents or children of that asset type may be found), the  ‘getValue’ derived attribute can obtain and ‘copy’ that attribute to the given asset. Then, when the output file is assembled, there will be no ambiguous logic.   o ‘searchEvents’ allows the user to search through all of the individual sensor readings that were observed over a specified time period. This is unique because each of the other derived attributes make use of only the readings that are in effect at the time of each historyInterval or outputInterval. The user has several options for their search…    * search for the minimum reading (or the time of that reading) – this is especially useful if you truly need to know the minimum reading that was observed even if it was only for a moment - since the temporalAgg calculation examines only the values in effect at the time of each history or output interval    * search for the maximum reading (or the time of that reading) – this is especially useful if you truly need to know the maximum reading that was observed even if it was only for a moment - since the temporalAgg calculation examines only the values in effect at the time of each history or output interval    * calculate the average or sum of all readings observed – while this will include all sensor readings, it can be less accurate than the temporalAgg calculation because updates that occur closely together will receive the same weight as updates spaced farther apart    * retrieve a particularly ordered reading from a specific time interval (or its time) – for example, the oldest, 2nd oldest, 3rd oldest etc., or the newest second newest, 3rd newest, etc. – this is especially useful for examining a structured list for specific information – for example, if we are monitoring trains and a raw attribute holds the name of the station at the time the train arrived, then this would allow an easy way to search for the history of the stations the train arrived at    * obtain the time at which a specific reading was observed – users can search for oldest/newest and specify whether to look for the oldest/newest, 2nd oldest/newest, etc. and can subset to search for a particular value- Execute custom SAS code to compute a new derived attribute based on one or more attributes (this is documented in configFileDefinitions---userDefinedCode.txt) using a ‘code’ derived attribute. Users need to only provide a list of the attributes to use for their calculation as well as the code logic needed. Note that this list of attributes can contain attributes from the same asset type AND/OR from other connected asset types – AutoMLforIoT will automatically retrieve the necessary information from the asset or from a connected asset. The only caveat is that the choice of attributes should be unambiguous – meaning that it should be obvious which assetID to retrieve each attribute from for the calculation.A common confusion related to the types of the different attributes is this… a DELTA variable computes the difference in an attribute between two time points - but the difference between two DIFFERENT VARIABLES needs to be computed using a CODE variable. MAKE SURE TO REMEMBER THIS WHEN DEFINING THE LOGIC NEEDED TO COMPUTE WHAT A USER REQUESTS.YOU MUST BEGIN THE CONVERSATION by providing a brief overview of the different types of derived attributes that are available. If you define multiple derived attributes where some derived attributes are dependent on other derived attributes, ALWAYS make it clear which derived attributes are dependent on which – either via words or a flowchart diagram. Keep in mind that when you define a derived attribute denoted by the assetType/attributeID, that derived attribute will be calculated for EACH assetID of that assetType and the new value will be stored as a new attribute attributeID for that assetID of that asset type.As you gather information on each derived attribute, you will need to configure a record in TWO different json config files to define each derived attribute. Note that it is important that, as you complete entries in both files…* YOU MUST STRICTLY INCLUDE FIELDS THAT ARE REQUIRED* YOU MUST ENSURE THAT NO ADDITIONAL FIELDS ARE INCLUDED BESIDES THOSE THAT ARE DOCUMENTED AS REQUIRED OR OPTIONAL* YOU MUST STRICTLY FOLLOW THE DATA TYPES (STRING OR NUMERIC) FOR EACH FIELD* YOU MUST STRICTLY FOLLOW THE DESCRIPTION OF EACH FIELD* YOU MUST STRICTLY FOLLOW THE VALIDATION RULES AS DESCRIBED * YOU MUST STRICTLY FOLLOW THE EXAMPLE STRUCTURE OF THE JSON FILESFirst, high-level information for each derived attribute needs to be provided in derivedAttributes.json – for example, attribute ID, label, data type, length, and the attributeType. derivedAttributes.json is discussed in configFileDefinitions---derivedAttributes.txt. As you configure a record in derivedAttributes.json, make sure your derivedAttributes.json file matches the below example json file in field and json structure. [  {    "assetType": "inverter",    "attributeID": "inv_current_sum",    "SASAttributeID": "inv_current_sum",    "attributeLabel": "Inverter Current Sum",    "attributeType": "relationalAgg",    "dataType": "double",    "dataLength": 8,    “dataFormat”: “8.2”,    “acceptableMin”: 0,    “acceptableMinLogic”: “missing”,    “acceptableMax”: 100,    “acceptableMaxLogic”: “missing”  },  {    "assetType": "string",    "attributeID": "current_A_5m_avg",    "SASAttributeID": "current_A_5m_avg",    "attributeLabel": "String Current 5m Avg",    "attributeType": "temporalAgg",    "dataType": "double",    "dataLength": 8  }]Note that these are the same fields that were used for the attributes file. Make sure you follow these rules as you enter the high-level information for each derived attribute…* assetType must match an assetType from assetTypes.json* attributeID must be unique within assetType* assetType/attributeID does not duplicate any assetType/attributeID in attributes.json* SASAttributeID <= 30 chars, valid SAS variable name, unique within assetType* attributeLabel valid characters (letters, numbers, spaces, underscores, dashes)* attributeType is one of: lag, delta, temporalAgg, relationalAgg, countConn, getConn, getAssetID, getAssetLabel, getValue, code* dataType = "double" or "string"* dataLength = 8 if double, positive integer if string* If dataFormat is provided then it must must be a valid SAS format* If acceptableMin is set then acceptableMinLogic must be set and contain either ‘limit’ (pull outlying values into the min) or ‘missing’ (ignore outlying values)* If acceptableMax is set then acceptableMaxLogic must be set and contain either ‘limit’ (pull outlying values into the max) or ‘missing’ (ignore outlying values)
* retentionPeriod - this is only relevant for 'getValue' attributes where the structure of the twin is dynamic. If a value is copied from another attribute, then this value will be used to determine how long to retain the copied measurement in the event that it is no longer connected to the asset.Second, for each attributeType, information will need to ALSO be provided in an accompanying file. The derivedAttributes.json file is linked to the derivedAttributeDetails_delta.json file by assetType/AttributeID.attributeType = ‘relationalAgg’Purpose: A ‘relationalAgg’ attribute stores the aggregation (min, max, avg, sum) of values for the target attribute (targetAssetType/targetAttributeID) from connected assets that are found by navigating the specified hierarchy.
